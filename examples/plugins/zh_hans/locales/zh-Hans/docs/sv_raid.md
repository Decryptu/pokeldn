# 太晶团体战

本地太晶团体战是《朱／紫》在 LDN 场景 7 中建立的会话，最多容纳四个站点。主机运行大厅，再向每个参与者发送一条初始化消息，包含四位玩家的宝可梦、首领及其 RaidPoint；各游戏机独立运行战斗。`bin/sv_host.py --raid-seed` 创建团体战供实机加入，`bin/sv_join.py --raid-pokemon` 加入游戏机主持的团体战。在两种模式中，本程序的玩家都会在对战开始时离开，宝可梦则作为游戏机的 AI 伙伴继续战斗。本文地址为《朱》4.0.0 解压后的 `main` 中的偏移；《紫》4.0.0 的相同代码位于相同偏移（[《朱／紫》](sv.md)）。

<a id="hosting"></a>
## 主持团体战

主机广播场景 7、四名参与者和连接密码 4970。游戏机通过 X → 宝可入口站 → 太晶团体战 → 离线搜索加入。`--raid-seed` 与四个上下文参数共同选择团体战（[种子](#the-seed)）；`--raid-pokemon` 指定我方出战宝可梦的队伍记录，由 PKHeX 检查；重复使用 `--raid-reward ITEM:QUANTITY` 可将种子的默认奖励替换为指定道具和数量。道具必须能放入《朱／紫》背包，即 PKHeX 辅助程序的 `bag` 列表：包括重要物品以外的所有口袋，并排除未发布道具。`--raid-partner TRAINER` 按空位顺序指定 NPC 搭档，可为游戏机留下的每个空位指定一名（一台游戏机有两位，两台有一位）；`--raid-partner-progress STAGE` 选择搭档所在阶段（[NPC 搭档](#partners)）。应用的“太晶团体战（主机）”入口携带以下参数。

    --channel 1 --scene-id 7 --max-participants 4 --code 4970 --scarlet-response --session-flags 0
    --session-packet-id 1 --no-session-ack --join-seq 0 --update-seq 0 --update-delay 0.02
    --rtt-probe --clock --net-stations 4 --record-delay 0.1 --record-spacing 0.003
    --host-player-id 00000000000000010000000000000000

团体战主机与交换主机在消息目标和发送时机上有所不同：

| | 团体战主机 |
|---|---|
| 发往网状网络的消息（RTT、0x80、0x81）、Session 站点列表 | 发往子网广播地址，而非游戏机地址（通过 ldn_mitm 时使用单播，因为它不向对端传递广播） |
| Net 0x11 | 使用同一序列号，重复发送直到收到 0x12 |
| 站点列表中的游戏机条目 | 使用游戏机加入请求中指定的玩家；使用占位玩家会导致游戏机已入座却未出现在大厅 |
| 站点列表 | 每 2 秒重发，直到收到游戏机的类型 6 |
| 开场 | 收到类型 6 后才发送：最先的十一条批量确认、0x81 端口 5 打开消息和 RTT 请求放入一个数据包；随后发送 0x81 端口 1 打开消息、通道表及端口 2 类型 6；20 毫秒后发送身份数据，每条记录间隔 3 毫秒 |
| 端口 2 类型 3 | 回应两条类型 9：主机站点代码为 0，游戏机站点代码为 1 |

开场的 0x7C、0x81 端口 5 和 0x80 端口 2 消息每 0.25 秒重复发送，直到得到确认；主机发出的每条确认都声明该数据流中尚未确认的最低序列号。

<a id="several-consoles"></a>
### 多台游戏机

`--raid-players N`（1 至 3，应用中的“加入的游戏机数量”）让最多三台游戏机进入同一大厅，按最低空闲站点索引 1 至 3 入座。游戏机共享大厅和开战过程；第一回合起各自在本机进行独立对战，拥有自己的 NPC 搭档并领取自己的奖励（[运行对战服务端的站点](#which-station-runs-the-server)）。主机为每台保留独立流，单台原本使用索引 1 的位置改用对应游戏机索引：

| | 索引为 *k* 的游戏机 |
|---|---|
| 加入响应 | 站点索引和加入顺序均为 *k* |
| 站点列表 | 全部已入座站点，我方在前；每次新入座或离开大厅，都向全部已入座游戏机发送下一序列号的列表，并重发直到各自回应类型 6 |
| Net 0x11 | 我方站点，随后按索引列出已入座游戏机，最后是加入方；每次座位变化都用下一序列号向所有站点发送 |
| 目标位图 | 在三个目标位中使用 `1 << k` |
| 批量确认 | 第 *k* 项 |
| 开场 | 0x81 端口 *k* 和 4 + *k*，即游戏机发送所用端口 |
| 端口 2 类型 6 | 我方及此前已入座成员，按加入顺序携带代码和数量 |
| 端口 2 类型 9 | 我方代码 0，各已入座成员使用各自代码，最后的游戏机使用代码 *k*；各已入座成员也收到该游戏机的信息 |
| 初始化数据 | 对应宝可梦放在槽位 *k*；空闲座位使用空槽 |

座位已满或战斗开始后，不回应新的加入请求；没有空位的游戏机也不会收到 Net 0x11。主持端丢弃标头和尾部未指定自身变量 ID 的包，以及位图中不含站点 0 的可靠消息，因为同一大厅的游戏机通过同一广播地址互相通信。

端口 2 槽位在 `+0x170` 保存成员，含 u8 代码和 u64 站点 ID；`0x138d208` 返回站点代码，非成员返回 0xfd。实机主机的类型 3 处理程序 `0x1981e94` 选择 0 到 7 中未被成员占用、也未被排队类型 9 使用的最低代码（`0x279c9a0`），随后按各成员自己的代码逐个广播类型 9，再为加入方广播一条。接收器 `0x18b68fc` 追加尚未列出的 `(code, id)`，不改变已有成员代码；遇到自身 ID 时，为各其他成员触发加入事件，并将此代码设为自身代码。类型 6（`0x12fbf8c`，构建器 `0xe457cc`，仅发给正在加入的站点）在 `+0xa0` 携带成员 ID、`+0xc0` 携带代码、`+0xc4` 携带数量、`+0xc5` 携带关闭字节；接收器 `0x279b9c4` 为每个成员重放类型 9。

大厅参与者就是端口 2 成员。Lua 大厅（区块 `be21e654`，接收器 `0.15829`；此处 `0.N` 表示区块主函数的第 N 个原型，从 0 计数）按发送方代码归档消息，没有代码的发送方归入 253。每台游戏机进入大厅时向其他成员发送状态 0x18 和自身宝可梦；收到 0x18 的站点回应自身准备状态和宝可梦。各游戏机在大厅中互相交换宝可梦信息。

可靠标头的接收检查（`0x6f0410`..`0x6f0430`）对 1 到 23 的任意目标数量检查接收者自己的位：字 `index >> 5` 的第 `index & 31` 位（位 0 对应站点 0）。实机发送端总是写入三，即站点容量 4（`0x44dfcb0`）减一（`0x6e71c4`），与实际站点数量无关。

与单台相同，主机将网络交给仍在网络上的最低索引站点；其他游戏机接收 is-migrating Net 0x11 和 NetStartHostMigration，不接收 Session 类型 7。发给各游戏机的 is-migrating 0x11 为所有在座站点指定接任主机顺序；接任主机回复类型 8 后才发给其他站点。所有游戏机以 0x12 回应各自的 0x11 后发送 NetStartHostMigration，之后不再发送普通 Net 0x11。所有游戏机离网或交接超时后结束运行。

决定游戏机能否留在同一对战的条件：

| 条件 | 代码 |
| --- | --- |
| 游戏机看到其他站点离开时，仅在迁移中保留该站点：is-migrating 0x11 设置 `[net+0x249]`，NetStartHostMigration 设置 `[net+0x1c0]`；否则从会话移除并重置 Net 站点 | 站点离开处理器 `0x69d08c`, `0x69d174` |
| 较新序号的 Net 0x11 移除所有已标记离开的站点 | `0x69e008`, `0x6b5074` |
| 接任主机最多等待 8000 毫秒，让各 Net 站点达到状态 2（新网络已发现）；移除仍为状态 1 的站点，发送 Net 0x11，等待所有 0x12，再发送 Session 类型 5 | NetHostMigrationJob `0x6a9cd4`, `0x6aa2a8`; `0x6d44f0` |
| 其他游戏机等待该类型 5 最多 10000 毫秒，随后失败 | `0x6dc024`, `0x6dc124` |
| 类型 7 的最后 u16 不超过接任主机已应用的列表序号 | `0x6d9164` |

两台模拟朱按此交接后，在接任主机网络上形成一个会话，类型 5 得到类型 6 回应，两边均无错误，并在空位加入一名 NPC 后继续对战。

Pia 主机在 LDN 参与者变化时向每个站点发送新的 Net 0x11：`0x69c310` 比较先前和当前连接状态，`0x69c79c` 递增唯一计数器 `[NetProtocol+0x60]`，向自身之外每个站点发送全部槽位，按 IPv4 升序排名（`0x6a05ec`）。LDN 加入方的 0x11 接收器 `0x69db14` 不根据条目创建站点（`0x6a2fac` 返回 0），而是保存主机地址和 ID，将排名复制到已有站点并回应 0x12。加入方站点来自 LDN 节点列表（`nn::ldn::GetNetworkInfo`、`0x6b43a8`），端口为 12345。

类型 5 接收器 `0x6d7f8c` 仅在 IPv4 和端口出现在节点列表中时（`0x6a8320`），通过 `0x6d840c` 创建新列出的站点；否则不发送类型 6，并将已应用序列号重置为 0xffff（`0x6d81a4`），以便再次评估相同列表。

Session 类型 9（`0x6d4ef0`）由加入方向主机发送，内容为 `09 | its constant id | count | count
constant ids`，列出尚未收到消息的站点（`0x6d4a60`），每 3000 毫秒重复。主机接收器 `0x6d940c` 将唯一指定的站点交给踢出任务（`0x6dc878`），并向每个站点重发站点列表。

游戏机加入后，团体战主机发送数据包 ID 0，否则已入座游戏机会丢弃较高 ID 后的消息（[docs/pia.md](pia.md#version-11-what-a-receiver-drops-scarlet-400)）。在 ID 87 的包之后用 ID 1 重发站点列表时，两台游戏机大厅中的第一台仍保留旧列表（实机和模拟器均如此），第二台显示“正在通信……”直到报告第一台没有回应。将之后的列表用 ID 0 发送后，两台模拟器和两台实机《朱》都列出彼此，并在主机离开后同步完成一场团体战。

形如 `10 00` 后接十四个随机字节的玩家 ID，未能让实机发送类型 6；匿名 ID `00000000000000010000000000000000`（`pia_connect.DEFAULT_PLAYER_ID`）则使其成功入座。

<a id="the-lobby"></a>
## 大厅

团体战消息是 0x80 端口 0 上的游戏消息：一个 u16 处理程序键、一个种类字节和一个步骤字节（[交换流程](sv.md#the-trade)），后接游戏序列化器的标头与载荷。

| 字节位置 | 字段 |
|---|---|
| 0 | 处理程序键，u16 |
| 2 | 种类、步骤：一个 u16 消息 ID（0x012f 初始化，0x0193 对战开始） |
| 4 | 每个发送方独立的 u16 计数器，由 `0xa583fc` 在每次发送时递增：实机主机大厅从 0x0105 到 0x010e，加入方从 1、2、3……递增 |
| 6 | 压缩方式，u32：0 为无压缩，2 为 LZ4 |
| 10 | 载荷未压缩大小，u32 |
| 14 | 网络对象 ID，u16，发送方 `0x14ede48` 未找到对象时为零 |
| 16 | 构造函数从不写入的两个填充字节（实机消息中的堆残留数据） |
| 18 | 载荷 |

| 键 | 种类 | 内容 |
|---|---|---|
| 0x3380 | 0x2c | 团体战描述：种类（DevID）、形态、星级、太晶属性、性别、遭遇记录编号 |
| 0x3380 | 0x2d | 参与者状态：0x00 未准备、0x01 准备就绪、0x0c 主机开始、0x0d 加入方回应开始、0x18 进入大厅、0x1e 主机拒绝迟到站点（`0.30822`） |
| 0x3380 | 0x2e | 参与者的宝可梦，加密后的 344 字节队伍记录 |
| 0x3380 | 0x2f | 战斗初始化数据 |
| 0x3380 | 0x30 | 大厅剩余时间，单位为秒（从 0x91 递减） |
| 0x0132 | 0x6e, 0x73 | 游戏机正在加载战斗，以及加载完成 |
| 0x3480 | 0x93 | 战斗开始 |
| 0x007b | 0x13 | 主机在 0x3480 后发送的战斗开始消息 |

实机加入方进入大厅时发送 0x18 和自身宝可梦，玩家选择准备后发送 0x01。七次实机团体战中，四名加入方在发送宝可梦后 1.9 到 3.6 秒发送 0x01，三名在主机于 5.39 秒开始前没有发送；七名均以 0x0d 回应开始并参加战斗。

标头对应消息对象的 `+0x40..+0x4f`。接收路径 `0x18bec54` 将 ID、计数器和对象 ID 复制回对象，不比较这些字段；不检查 LZ4 返回值，未压缩大小仅用作输出容量。

键 0x007b 的战斗开始帧包含 12 字节端口地址（三个 u32）、一个 u32 长度和载荷；载荷前 32 字节为 `0x1227714` 原样复制的标头结构：0x00 的 u32 类型、0x08 和 0x10 的 u64、0x18 和 0x19 的 u8，以及 0x04 和 0x1a..0x1f 的填充。消息 15 在 0x18 保存 `05 05`，随后为填充 `07 26 5a 00 00 00`；消息 16（类型 0x46，构建器 `0x2898350`）的构建器从未写入的填充中保存 `ceaf29`。读取方 `0xf5a2fc`（+0、+8、+0x10、+0x18，最后一项接受 5 或接收者自身索引）和类型分派 `0xe10088`（0x46 处理程序 `0x2897afc`）不读取填充。`0x14ab234` 在接收者没有端口注册该地址时丢弃帧：消息 15 发往 (0x2713, 1, 2)，消息 16 至 20 发往 (0x2713, 3, 5)，0x2713 是对象 `+0x40` 的运行时 u32，写入方未追踪。
模拟《朱》4.0.0 接收填充清零的消息 13、15、16 后，首次发送就确认所有战斗开始消息，并以主机宝可梦开始对战，与使用实机字节时相同。
模拟《朱》4.0.0 在主机发送消息 15、16 后 13 毫秒进入保留分支 `0x14ab210`：`0x14ab234` 匹配战斗开始帧地址，`0x14ab298` 保存它。

对战按类型读取消息 16。读取方 `0xe0fd68` 弹出帧，在标头 +0x08 的 u64 为 0 时按 +0x00 类型分派（`0xe10088`）：类型 0x46 以 `[reader+0x48]` 为唯一参数调用 `0x2897afc`，`0x2897afc` 在对象 `+0x71` 写入 1。该参数是逐帧更新 `0x289358c` 自身的对象：`0xfa4bb4` 通过初始化程序 `0x28950c8` 创建（`+0x40` 为战斗状态机，此处称 `sm`；`+0x48` 为推进对象 `[sm+0xa8]`，`+0x50` 为读取方 `[sm+0xb0]`），保存到 `[sm+0x148]`（`0xfa4c18`），并赋给 `reader+0x48`（`0xfa4c68` 处的 `0x2892ab4`）。状态 `0x28932a4` 以 `[sm+0x148]` 调用更新（`0x28932d0`）。更新读取 `+0x71`：为 0 时驱动读取方（`0xe0f014`），调用 `0xfc363c([+0x48], 0)`；为 1 时停止驱动，每帧调用 `0xfc363c([+0x48], 1)`，返回 true 时由 `0x28935b8` 清零。参数为 1 时，`0xfc363c` 从 `+0xa8` 的来源取出项目，在 `[+0xb8]+0xa0` 目标为空时交给 `+0xa0` 和 `+0xb8` 的目标。目标包含双端队列（map `+0x60`、起点 `+0x98`、大小 `+0xa0`），每帧推进各元素的 vf `+0x68`（`0xfc38dc`）。更新结果未使用（`0x28932d4`），该路径不会写状态机 `+0x68` 的状态。
模拟《朱》4.0.0 在类型 0x46 分支弹出的帧携带主机写入消息 16 填充的标记（`46000000 d16a1616`、`0500 161616161616`），因此该帧就是消息 16。弹出发生于网络断开、Error 7 提示之后，首次指令菜单之前，来自更新自身的驱动调用（返回地址 `0x28935d0`，随后 `0x28932d4`）。

4.0.0 的判断逻辑不读取填充。接收路径载入序列化器标头末两字节（`0x18bec98`），不比较就存入 `+0x4e`（`0x18bece4`）；49 个消息类中，只有序列化器 `0x290b150` 和 `0x14c7904` 读取 `+0x4e`，用途是写出标头。战斗开始读取方 `0xe0fd68`、`0xe106a4`、`0xf5a2fc`、`0xf5a810`、`0xf5bc10` 读取 32 字节标头的 +0x00、+0x08、+0x10、+0x18、+0x19；`0xf5a454` 和 `0xf5ae40` 将全部 32 字节复制到 `0xf5bb4c` 重发的帧，不比较它们。传输复制（`0x14ab150`、`0x14ab234`、`0x16a319c`）只比较 12 字节地址。

团体战主机在 0x7C 端口 1 公布的通道表包含六个键，使用 zlib 压缩：连接交换的四个键（`0x007b`、`0x0132`、`0x0232`、`0x0332`），以及 `0x3380`、`0x3480`。实机加入方分两条消息公布它们：先发送四个键，0.79 秒后发送团体战的两个键。端口 2 携带主机的类型 6：种类 5、容量 4 下的类型 7 会话块，后接四个槽位的列表，首个槽位为主机站点 ID（`port2.build_session`）。

`pokeldn.sv.raid.RaidHost` 向单台游戏机按顺序发送消息，每条依据端口 2 回应后的时刻，并等待游戏机完成上一阶段；`pokeldn.sv.raid.RaidGroup` 保存同一大厅多台游戏机共用的状态。单台游戏机在 5 秒内准备时，序列号与实机主机相同：

| 序列号 | 消息 | 释放条件 |
|---|---|---|
| 1 | 描述信息（zlib，INITIALIZED） | 游戏机自己的大厅宝可梦（0x2e） |
| 2, 3 | 状态 0x18、我方宝可梦 | |
| 4, 5, 6 | 计时器 0x91、0x90、0x8f | 0.73、1.76、2.75 秒 |
| 7 | 状态 0x01 | 3.19 秒 |
| 8, 9 | 计时器 0x8e、0x8d | 3.76、4.79 秒 |
| | 每次剩余时间减少时发送计时器 | 首台游戏机回应后 0.73 秒开始，每秒一次 |
| 10 | 状态 0x0c，开始 | 5.39 秒，且 `--raid-players` 台游戏机全部入座并发送 0x01，或计时器已发送 0 |
| | Net 0x50，属性状态 7 | 游戏机的状态 0x0d |
| | Session 站点列表，下一序列号 | 游戏机的 Net 0x51 |
| 11, 12 | 初始化数据，两个分片 | 游戏机针对它发送的类型 6 |
| 13 | 加载完成，`0x320173` | 游戏机的 0x6e 或 0x73 |
| 14 | 战斗开始，`0x803493` | 游戏机的 0x73 |
| 15 到 20 | 战斗开始消息 | 游戏机的 0x93；随后间隔 0、0.10、0.12、0.16、0.18 秒 |

计时器显示距主持端大厅截止时间剩余的秒数：实机主机打开 180 秒大厅，每秒发送一次（`0.27104`），所以表中的 0x91 出现在打开大厅后 35 秒。我方计时器从首台游戏机回应时的 180 开始；后来加入的游戏机收到当前剩余值。游戏机状态 0x00 或 0x18 会撤回其 0x01；宝可梦消息不会撤回，因为已准备的游戏机会向每个新成员重发宝可梦。

游戏代码中，加入方立即用 0x0d 回应 0x0c，不检查准备状态；计时器到 0 后等待初始化数据（`Raid_Start_Ready`、`0.27137`），只有主机发起战斗。没有准备却已收到初始化数据的加入方，在计时结束前结束大厅（`0.27104`），同样进入战斗。实机主机玩家首次选择时准备，第二次选择时发送 0x0c（`0.27095`）。`Raid_Start_Ready` 进入时关闭主机和加入方菜单的前三项（`f6277C172(false)`）；主机仅在其他成员全部准备后重新启用开始项及菜单，任一成员未准备则再次关闭，因此玩家只能在所有加入方准备后开始。`f6277C172(false)` 是隐藏还是禁用菜单项尚未确定。计时到 0 时，无人准备则解散，否则开始。`Raid_Start_Go`（`0.27140`）重复发送 0x0c 直至每名成员回应 0x0d，再发送初始化数据；槽位 *k* 放代码为 *k* 的成员宝可梦。我方同样等待全部游戏机的 0x0d，在全部准备或计时到 0 时开始。

受阶段条件控制的消息在对应里程碑后 50 毫秒发送；Net 0x50 和站点列表每 0.5 秒重发，直到得到回应，团体战消息也每 0.5 秒重发，直到得到确认。实机曾对初始化消息回应 0x73 而不发送 0x6e，因此消息 13 等待两者中的任一种。

最后一台游戏机的消息 20 发送五秒后，主机像离开的实机主机一样将网络移交给游戏机（[离开](sv.md#leaving)）：每秒发送指定游戏机的 Session 类型 7，直到收到其类型 8；每 0.5 秒发送处于迁移形式的 Net 0x11，直到收到其 0x12；每 0.3 秒发送 NetStartHostMigration `01400000`，直到游戏机离开网络或经过 4 秒。如果改为在消息 20 后 5 秒销毁网络，四次实机团体战中有一次在战斗开始时显示 2318-0006，之后战斗继续以离线方式运行。

Net 0x50 使用交换主机的属性主体（`NET_PROPERTY_BODY`），其中序列号为 1，包含网络 ID，第 27 字节为 7，并在 +38 处携带主机的 132 字节应用数据；整体以 zlib 压缩，消息标志为 0x31。在 0x31 下不压缩发送时，未得到 0x51。

消息 0x2f 携带一条 0xaa0 字节记录，以 LZ4 压缩（仅使用块格式，`pokeldn.sv.lz4`）：

序列化器 `0xe327fc` 通过 `0xe329b4` 从消息对象的 `+0x440`、`+0x448`、`+0x450`、`+0x458` 和 `+0x50` 写入五条记录（每条 0x158 字节），再写入 `+0x58` 的四个四字和 `+0x78` 的 0x3c8 字节。对象大小为 0x460 字节，由 `0x18bb4fc` 创建，`0x18bb5f8` 设置类型；`0x1592b7c` 写入序列化器标头并选择压缩方式，`0x1592dac` 和 `0x1592e80` 执行 LZ4（`0x71d940`）。RaidPoint 整体复制：`0x1bae670` 调用 `0x1bae760`，通过反射字段读取器 `0x1baff98`（取 `+8` 处指针，或取清零的 0x3c8 字节单例）取得数据，再由 `0x1bb0018` 写入 `+0x78`。

团体战表中，全部六星记录的 `raidTimeData` 均启用，`gameLimit` 为 450、`commandLimit` 为 60；全部一星记录未启用，`gameLimit` 为 300，其余为零。一个实机黑色结晶（记录 6045）保存 1、450、0、60；一个实机三星结晶（记录 3019）保存未启用布尔字节、三个残留字节，再后为零。
两个实机结晶的 0x3b5..0x3b7、0x3d4..0x3d7 和 0x3e4..0x3e7 均保存残留字节。

行动配置按游戏团体战表中记录的 `bossDesc` 顺序排列。行动值 0 表示无，1 重置首领能力变化，2 重置玩家能力变化，3 使用招式，4 夺取太晶珠能量；触发时机 0 无、1 时间、2 HP。行动值为触发时的剩余 HP 或时间比例；护盾前两值分别是 HP 和时间比例，任一满足即展开。2026 年 8 月七星仆刀将军的 Serebii 脚本行动与记录读取结果相同。一至六星 HP 系数为 500、500、800、1200、2000、2500。

实机地点的奖励行依次为种子的固定奖励、随机抽取奖励、主机加成奖励：三行适用对象 4、一行适用对象 5。固定行的对象来自奖励表 `SubjectType`（0 所有玩家、1 主机、2 加入方、3 一次）；游戏枚举 `RaidRewardItemSubjectType` 没有 4 或 5。两个实机地点的对象 4 行均为同一生成器额外抽取三次，对象 5 行则为首领太晶碎片，数量由 `RaidGemItemRewardBoost` 按难度给出（一至七星分别为 0、0、2、5、10、12、0；三星 2，六星 12）。餐力表读取方 `0xef885c` 读取一个团体战字段 `AddRewardSlots`。奖励行第三个字在银色王冠随机行中为 1，其他为 0。

模拟《朱》4.0.0 加入方接收适用对象 0 至 5 各一行时，奖励画面列出 0、2、3、5，不列 1、4。餐力“团战力：幽灵 Lv. 1”生效时，面对钢太晶首领不列对象 4，面对幽灵太晶首领则列出；发送三行对象 4 时仅列第一行。面对幽灵太晶首领发送四行对象 4 时，团战力 Lv. 2 列出前两行，Lv. 3 列出前三行。

生效的餐力在内存中保存为 u32 种类、u32 属性、u32 等级及 f32 剩余秒数；食用时为 1800 秒，在场景中倒计时。上述等级 2、3 的检查及下述检查，修改了 Jambon-Beurre 三明治“团战力：幽灵 Lv. 1”记录的等级和属性字。

在黑色结晶地点（种子 `09F3E337`、妖精太晶属性的仆刀将军）上启用“团战力：妖精 Lv. 3”时，同一加入方列出 19 行中的 18 行：所有对象 0 行、对象 2 行、三行对象 4，以及对象 5 的妖精太晶碎片 ×12；不列对象 1 行。唯一带稀有道具标志的对象 4 银色王冠排在画面第一项，其余保持地点中的顺序。地点由 `raid_point` 生成，只替换动作配置（HP 系数 100，其余为零），以便单个加入方获胜；星级、结晶、`raidTimeData` 及奖励行均来自该种子。

《朱》4.0.0 的 Lua 奖励过滤函数 `C07C34FC3B976E5A7.F316609DEA110601D`（源代码第 78707 至 78765 行）为所有玩家保留适用对象 0，为主机保留对象 1，为加入方保留对象 2；一次性奖励的资格参数为真时保留对象 3。它保留前 N 行对象 4 的奖励，其中 N 是当前生效且与首领太晶属性匹配的团战力最高等级。餐力种类 5 为团战力，属性 18 匹配所有太晶属性。对象 5 要求接收方背包中持有道具 2481，即晶耀护符。每遇到一行对象 4，行计数器都会递增。测试框架提供原生环境查询函数后，执行未经修改的 Lua 函数：团战力等级 0 至 3 分别保留零、一、二、三行对象 4，对主机和加入方均如此，与是否持有护符无关。属性不匹配时不保留任何行；多个匹配的餐力同时生效时采用最高等级。

若主机要复现零售版游戏的奖励构建方式，应保留每行固定奖励的适用对象，以及每行奖励的稀有道具标志；普通随机抽取奖励使用对象 0，随后继续同一抽取序列，追加三行对象 4 的随机奖励。对应难度的太晶碎片加成数量大于零时，再追加对象 5 的奖励。每位接收方分别按自身餐力和护符判断领取资格。

计时器初始化函数 `C2D7F486425487755.F0C64BA9B6853E61A`（源代码第 79486 至 79513 行）在 `raidTimeData.active` 为真时使用传入的时间字段；为假时，团体战默认使用游戏时限 300、指令时限 60、客户端时限 0、复活时间 30、AI 间隔 17 和 AI 间隔随机幅度 6。将六星表的数据传入未经修改的 Lua 函数执行，上述值依次为 450、60、0、0、0、0；RaidPoint 全部为零时采用默认值。两个函数均位于 Lua 代码块 `be21e65463b9a98f`，SHA-256 为 `c1a4f4e2625912cf0b739a642a79ba3357df0557a544b92da22a6cb139de2815`。

`raid_point` 按实机主机方式构建种子奖励：固定行使用表中的适用对象，随机奖励使用表中的稀有标志，再抽取三次作为对象 4，并按难度添加对象 5 的太晶碎片加成。种子 7B741233（三星）和 09F3E337（黑色结晶）的 45 行与实机地点逐字节一致。携带晶耀护符的实机《朱》加入方收到 7B741233 的奖励行后，显示冰太晶碎块 ×1 和 ×2：保留对象 5 的行，没有主机专属对象 1 的 ×1 行。自选奖励写入对象 0，不加额外行，因此加入方获得每项。实测将某行改为先机球 ×500、清空其他行且保留一行加成后，实机按写入内容发放奖励。

<a id="partners"></a>
## NPC 搭档

各游戏机会用相同的 NPC 训练家填补大厅成员未占用的位置，取决于 Lua 将其称为 `randSeed`（0x3d8 处的 u64）和 `raidNpcGroupID`（0x3e0 处的 u32）的两个 RaidPoint 字（`0.4453`）。getter 对应的原生函数读取 RaidPoint 前 0x20 字节之后、大小为 0x3c8 的结构中的 +0x3b8（`0x1be5ac0`）及 +0x3c0（`0x1be5c20`）。加入方的初始化处理程序读取两者（`0.15829`）；实机主机每次开始抽取新的 `randSeed` 并写入两者（`Raid_Start_Go`、`0.27140`）。完整 u64 为 xoroshiro128+ 提供种子（原生函数 `0x17ebec0`），第二个字使用 `0x82A2B175229D6A5B`。游戏机抽取三名训练家（`0.7804`），每次在剩余 n 名中执行 `next_int(n)`，将结果限制到 n − 1 所需位数，遇到不小于 n 的值重新抽取，并从池中移除已选训练家；完整池的上限依次为 18、17、16。空位按槽位顺序取结果（`0.4455`）：只有一个空位时，无论位置都取第一名。

每个搭档的记录从相同的 `randSeed` 取五次 xoroshiro128+ 随机数，同一场对战的搭档共用这些结果（`raid_partners.identity`）：第 0 次为加密常数，若为 0xffffffff 则重抽；第 1 次为 TID | SID << 16；第 2 次为 PID，若会产生异色则翻转位 28；第 3 次为身高、第 4 次为体重，均使用 0x30 + next_int(0xa0)。其余字段来自下述训练家条目，语言为 2，亲密度为该种类的基础亲密度。仅凭种子、阶段和等级，这些规则即可得到五场模拟团体战的全部十份搭档记录，每份 0x148 字节。

团体战开始流程（`0.4455` → `0.4459` → `0.4901`）将每个搭档的 `poke1` 表、等级和 `randSeed` 交给 Lua 绑定 `f92C18AA6`（`0x1905a10`）。它构建以 `randSeed` 为种子的 pml InitialSpec（`0x1905ce0`），将表转换进该结构（`0x160ffd0`），再创建 PokemonParam（`0xdebe4c` → `0xdec698` → `0xdef2b8`）。指定种子的 `0xdef2b8` 为规格中未设置的字段，从自身 xoroshiro128+（`0xdf78bc`、`next_int` `0xdf78d8`）依次抽取：EC、ID、PID、个体值、特性、性别、性格、身高、体重、体型（`0xdf011c`）。绑定的第三个参数为真，因此转换器将随机的身高、体重或体型改为 M 类（SizeType 3，`0x1611cc4`），由 `0xdf011c` 以 0x30 + next_int(0xa0) 抽取；真正随机的大小则使用 next_int(0x81) + next_int(0x80)。在 unicorn 中执行 `0xdef2b8` 时，只有 M 类能重现十份记录的 EC、PID、身高与体重。

当条目的 `sex` 为 0，转换器在抽取加密常数之前，使用该未设置字段决定性别：种类的雌性百分比至少为 (2^64 - 1) mod 100 = 15 时为雌性，低于 15 时为雄性；恰为 50 时由绑定的第四个参数 0 决定为雄性。单一性别或无性别种类保留自身性别（`0x1611d1c`）。卡蒂狗和风速狗为雌性，小磁怪、三合一磁怪和青铜钟无性别，其余搭档为雄性。`gemType` 为 0 时，太晶属性由 `0xe78418` 读取的种类表决定，键值为种类编号 × 10000 + 形态；双斧战龙使用龙，土王使用地面。

0x3e0 处的 u32 选择池，对应数据表字段 `difficulty_0`*N+1*（`0.7797`）、训练家及其宝可梦（下表）：0 和 1 使用前 16 名，2 使用全部 18 名，3 和 4 也使用全部 18 名。池来自 RomFS 表 `world/data/raid/raid_trainer_01`（16 行，阶段 0、1）、`_02`（18 行，阶段 2）和 `_03`（18 行，阶段 3、4）。各行包含 `raidTrainerInfo`、训练家 ID `raid_assist_NPC_1` 至 `_52`、`npcPresetIndex`（行索引，`0.4459` 将其传给训练家模型）和 `nameTextLabel`（每个池从第 0 行的 `TRNAME_RAID_ASSIST_01` 开始）。训练家的宝可梦是 `world/data/trainer/trdata/trdata_array` 条目的 `poke1`，类型为 `PokeDataBattle`：种类、形态，预设等级 16、40 或 80，`tokusei` 为 2 至 4（特性位置 1、2 或隐藏特性），三个招式，`gemType`（2 + 太晶属性），个体值 31/10/31/31/10/31（HP、攻击、防御、速度、特攻、特防），努力值 HP 252、防御 128、特防 128，勤奋性格、精灵球、非异色、`sex` 0、体型 128、无携带道具。`raid_trainer_04` 至 `_07` 列出野外训练家（`area04_trainer_*`、`area05_trainer_*`），尚不清楚谁读取它们。`scripts/gen_sv_partner_data.py` 将池解码到 `pokeldn/sv/data/raid_partners.json`（`raid_partners.game_pool`）。搭档实际等级为 int(0.8 × 战斗位置 0 中主持方宝可梦的等级)，不使用预设等级（`0.4455`、`0.4901`），因此 Serebii 的等级 16、40、80 分别对应等级 20、50、100 的主持宝可梦。pokeldn 团体战的位置 0 使用 `--raid-pokemon`。实机《朱》上，主持宝可梦等级为 100 和 37 时，Eli 的沙奈朵分别为 80 和 29，与游戏机玩家自身宝可梦的等级（100、84）无关；早期池中 Eli 的奇鲁莉安及 Charlotte 的姆克鸟，在等级 100 的主持宝可梦旁也为 80，超过池所标注的 16。阶段为 5 时，实机《朱》的搭档变成以首领命名的皮卡丘，之后对战崩溃，因此 `raid_point` 拒绝高于 4 的阶段。

<a id="the-seed"></a>
## 种子

团体战由 32 位种子和游戏机状态决定：版本、地区（帕底亚、北上乡、蓝莓学园，表前缀分别为 `""`、`su1_`、`su2_`）、剧情进度及结晶。xoroshiro128+ 从种子和常量 `0x82A2B175229D6A5B`（`0xe29340`）开始；第一次抽取范围为一百个值，按剧情阶段的边界决定普通结晶的星级（黑色结晶固定为六星）；第二次依据该星级和版本中的出现概率选择遭遇。`0xe29404` 以 `%sdifficulty_%02d` 构建表名，并将记录传给读取 `raidEnemyInfo` 的 `0x1eab5e4`；`0x2935b68` 遍历全部三个前缀和六个等级。随后，相同种子重新初始化 xoroshiro，依次生成首领的 EC（种子低半部分加 `0x229D6A5B`，因此可从首领记录反推出种子）、模拟训练家 ID、PID、满个体值项、其他个体值、特性、性别、性格（颤弦蝾螈从对应形态的列表中选择）、身高、体重及体型大小，与 PKHeX 的 `Encounter9RNG.GenerateData` 相同；太晶属性和奖励抽取各自再使用一个重新初始化的生成器。

`pokeldn.sv.raid_encounter` 基于 `pokeldn/sv/data/raid_base.json` 实现上述流程；数据由 `scripts/gen_sv_raid_data.py` 根据 Tera-Finder 的遭遇列表和奖励表、PKHeX 种族数据，以及游戏 RomFS 中十八张 `raid_enemy_XX_array` 表生成（`arc/worlddataraidraid_gem_item_reward_boostdata.bin.trpak`，带自身 `.bfbs` 架构的 FlatBuffers）。全部上下文的 12600 多个种子，首领均与 PKHeX.Core 26.8.26 逐字段相同，包括帕底亚六种遭遇（记录 5094 到 5099）：实机表的太晶规则为 0（种类自身属性），PKHeX 保存为 1（任意属性）。结晶构建器 `0xe26ff0` 读取 `gemType`，规则 0 和 1 都从 18 种属性随机选择（`0xe27414` 的 `cmp w9, #2`，重复抽取直至小于 18），与 PKHeX 相同；通用转换器 `0x160e108` 将 0 视为种类属性，但不在团体战路径上。种子 `BD13FB43`（紫、帕底亚、四星）生成的首领记录与实机初始化数据逐字节相同；`7B741233`（朱、帕底亚、五星）与法语实机《朱》相同，只有昵称与语言不同：实机写入自身语言和对应的种类名称（`Embrylex`、3），生成器使用英语（2）。游戏机始终以自身语言显示首领名称。

团体战表中的种类使用游戏的 DevID：到 916 为止与全国图鉴编号相同，从 917 起使用游戏自己的顺序（小锻匠 957 对应 1000），转换由 `gen9.internal_index` 完成。描述信息和 RaidPoint 同样携带 DevID：向实机《朱》发送种类 1000 的描述和 RaidPoint 后，大厅显示并在战斗中出现小锻匠。

黑色结晶记录的战斗等级为 90，携带努力值（例如防御 128、特防 128），捕获等级为 75；普通结晶记录的两个等级相同，努力值为零。初始化数据中的首领记录和 RaidPoint 概要携带战斗等级和努力值，RaidPoint 的 `+0x2c` 携带捕获等级。种子 `09F3E337`（朱、帕底亚）生成的黑色结晶首领与法语实机《朱》一致，只有昵称和语言不同。

<a id="event-raids"></a>
## 活动团体战

宝可入口站新闻分发包含五个文件：`raid_enemy_array`、`fixed_reward_item_array`、`lottery_reward_item_array` 和 `raid_priority_array` 为 FlatBuffers，布局与基础表相同；`event_raid_identifier` 为 u32，重复优先级表的 `VersionNo`（`20221202`）。自 1.3.0 起，分发会为各补丁分别携带这些文件（`_1_3_0`、`_2_0_0`、`_3_0_0`），旧副本被置空；读取时使用最新版本。`raid_enemy_array` 记录与普通记录相同，另外包含 `RomVer`（0 为两个版本、1 为朱、2 为紫）、`DeliveryGroupID`、以星级表示的 `Difficulty`（7 为七星团体战）、`CaptureRate`（0 不可捕获、1 普通捕获、2 仅可捕获一次）和各自的奖励表名称。其 `BossPokePara` 固定普通首领随机生成的部分字段：

| 字段 | 活动记录 |
|---|---|
| `Sex` | 0 随机生成；1 雄性、2 雌性，跳过性别随机抽取 |
| `Seikaku` | 0 随机生成；否则为性格编号加 1，不进行随机抽取 |
| `TalentType` | 1：`TalentVnum` 项满个体值；2：使用 `TalentValue` 的六项个体值，不进行随机抽取 |
| `RareType` | 0 随机生成；1 永不异色：若 PID 与模拟训练家构成异色，则翻转位 28；2 必定异色：重写高半部分，使异色异或值为 0 |
| `ScaleType` | 0 抽取两次；1 到 5 分别在 0-15、16-47、48-207、208-239、240-255 中抽取一次；6 使用 `ScaleValue` |
| `Item`, `EffortValue` | 首领携带道具和战斗努力值（七星皮卡丘携带电气球） |

记录的 `TimeDesc` 就是其 `raidTimeData`，RaidPoint 在 0x030 处携带此值。所有七星记录都启用此数据，`gameLimit` 为 450 到 900、`commandLimit` 为 60；五条五星记录同样启用（`gameLimit` 为 320 到 450）。其余 420 条记录未启用（2026-09-06 的活动库）。

一个团体战地点属于 1 到 10 的某个分发组；`raid_priority_array` 记录各组地点数量。xoroshiro 从种子生成普通结晶星级所用的百分位随机值并丢弃，随后在当前游戏版本、剧情阶段允许星级的组内记录总权重中抽取一个值，按表顺序选择覆盖此值的记录 [PKHeX `EncounterDist9.GetIsPossibleSlot`]：

| 进度 | 阶段 | 可抽取星级 |
|---|---|---|
| 游戏初期、太晶团体战 | 0 | 1, 2 |
| 三星 | 1 | 1 到 3 |
| 四星 | 2 | 1 到 4 |
| 五星、六星 | 3 | 3 到 7 |

权重为 0 的记录不会被抽取。首领和太晶属性按普通团体战的方式生成，同时应用记录的固定字段。奖励先使用记录的固定奖励表，再从分发自己的随机奖励表抽取；七星团体战的抽取数量与六星相同。有权重但没有道具的随机奖励槽仍计入总权重，却不发放道具，数量为 0 的行也一样。2023 年首轮索财灵活动在《朱》中的随机奖励表存在此问题：全部槽为空或数量为 0，因此仅发放固定奖励。

`pokeldn.sv.raid_event` 读取分发目录（[EventsGallery](https://github.com/projectpokemon/EventsGallery) 活动目录或其 `Files`），生成主持端准备的 `Raid`：

    ./.venv/bin/python bin/sv_host.py ... --raid-pokemon FILE --raid-seed 52E6B438 \
        --raid-event "EventsGallery/Released/Gen 9/SV/Raid Events/002 Charizard the Unrivaled" \
        --raid-version scarlet --raid-progress 6star [--raid-event-group 1] [--raid-catch-normal]

RaidPoint 携带记录的捕获规则，结晶类型使用存档的团体战内容值：2 为活动、3 为七星活动（Tera-Finder `RaidContent`）。

模拟《朱》4.0.0 加入方参加了两种活动。伊布精选活动（20221125），种子 `00000002`、游戏初期、结晶 2：一星伊布可捕获，奖励画面按种子奖励行的顺序显示。最强喷火龙（20221202），种子 `00000001`、六星进度、结晶 3，`raidTimeData` 为 1, 600, 0, 60：首领显示为“最强喷火龙”，时间条每分钟约缩短十分之一，时限为 600 秒，而游戏机自身默认为 300 秒。

通过 ESP32 开发板连接的实机《朱》也参加了同样两场团体战：战胜一星伊布后出现捕获选项并获得种子对应奖励；喷火龙显示为七星，时间条缓慢缩短。实机还参加了普通黑色结晶团体战（种子 `00000004`，啪嚓海胆），其 RaidPoint 携带记录的 `raidTimeData` 1, 450, 0, 60。

应用的“太晶团体战（主持）”入口从自行下载和更新的活动库副本中选择活动，并将版本、进度、结晶限定为该活动可生成的选项（[团体战活动](gui.md#raid-events)）。结晶选项来自 `raid_event.dens`：优先级表中有地点、该版本中有记录的分发组；波荡水精选活动在《朱》中提供组 1，在《紫》中提供组 2。

捕获规则 2 表示每个存档只能捕获一次：所有七星记录均使用此规则，各轮波荡水和铁斑叶、帝牙卢卡和帕路奇亚精选活动以及异色烈空坐也一样。存档保存已捕获的记录编号，每项八字节，含编号和捕获标志（区块 `0x8B14392F`；从 2.0.1 起，击败标志位于 `0xA4BA4848`，PKHeX `RaidSevenStar9`）。复刻活动重复使用编号（波荡水七轮均为 2023022801），所以某轮已捕获会阻止其他轮捕获。异色灾祸之宝精选活动的记录为 0，无法捕获。主持端概要说明规则（`caught once per save`、`cannot be caught`）。

游戏机根据大厅描述信息中的记录编号（0x2c）检查此列表。已捕获最强超梦（2023090101）的实机《紫》收到主持端对应描述后，在大厅提示无法捕获太晶宝可梦；无论 RaidPoint 捕获规则写入 1 还是 2 都一样，因为战斗开始前不会发送 RaidPoint。面对存档已捕获的最强鲤鱼王（2026071701），同一游戏机的行为如下：

| 描述信息中的记录编号 | RaidPoint 捕获规则 | 大厅 | 获胜后 |
|---|---|---|---|
| 2026071701，原记录编号 | 2 | 提示无法捕获 | 无捕获选项 |
| 2026071701 | 1 | 提示无法捕获 | 无捕获选项 |
| 2026071799，替代编号 | 1 | 无警告 | 可捕获 |
| 2026071799，再次使用 | 1 | 无警告 | 可捕获 |

只要存档将记录编号列为已捕获，无论 RaidPoint 的捕获规则如何，获胜后都不能捕获（第二行）。按规则 1 捕获时，不会把替代编号加入列表（第四行）。`--raid-catch-normal` 将仅限捕获一次的记录作为普通捕获提供：RaidPoint 捕获规则为 1，描述信息使用替代记录编号，即原记录日期加后缀 99（`raid_event.stand_in`：2026071799）。没有分发使用此后缀（最大仅为 14）。概要显示 `served as a normal catch of record 2026071799`。不可捕获的记录仍为 0。

替代编号仅出现在描述信息中：首领记录及 RaidPoint 除捕获规则外与活动逐字节相同，PK9 字段也不保存记录编号。PKHeX.Core 26.8.26 的团体战遭遇（`EncounterDist9`、`EncounterMight9`）同样没有记录编号，只有分发组，因此捕获合法性不依赖它。除仆刀将军第二轮（晚于该版本）外，对活动库中所有仅限捕获一次的记录，在各可用版本下分别测试三个种子，并额外测试鲤鱼王种子 `000FD5D7`，共 331 场团体战：将主持端发送的首领记录按 PKHeX 自身的遭遇转换方式赋予测试训练家后，与 PKHeX 从同一种子生成的捕获记录相同，且合法。七星捕获只有带最强之证（`RibbonMarkMightiest`）才合法，游戏机会赋予此证章；游戏机按编号 2026071799 捕获的鲤鱼王带有此证章。

固定奖励行的 subject 3（`Encounters.txt` 中的 `Only Once`，七星团体战的招式学习器和特性膏药）是另一条规则；`raid_point` 使用表中的适用对象，各游戏机的奖励画面分别筛选。活动首领可以是任意种类，因此常规团体战首领范围外的种族数据、招式 PP 和名称来自 `pokeldn/sv/data/species.json`（`scripts/gen_sv_species_data.py`，使用与 `raid_base.json` 相同的 PKHeX 修订版本）。

针对 EventsGallery 的 153 个分发目录（2026-09-06）：每张表解码后均与其 JSON 相同；pkNX 提取器生成的分发及七星遭遇与 PKHeX.Core 26.8.26 的 174 条及 55 条全部一致（仆刀将军第二轮晚于该版本，`000 Base Data` 是游戏自身占位数据）。对每个活动、版本、阶段和组各测试四十个种子，20 080 个首领均与 PKHeX `GenerateSeed32` 逐字段相同，且 PKHeX 允许各记录在对应阶段生成。`scripts/check_sv_raid_events.py` 找到各分发的全部 537 条遭遇，并确认其生成团体战与 `Encounters.txt` 一致，索财灵异常轮次除外。PKHeX 的 229 条遭遇分别使用种子 `00000001`、`12345678`、`9ABCDEF0`、`DEADBEEF`、`52E6B438` 和 `0000F00D`，生成的加密常数、个体值、特性编号、性别、性格、身高、体重和体型大小均与 `boss_fields` 从对应活动库记录生成的结果一致。

<a id="finding-a-seed"></a>
## 查找种子

应用的团体战种子字段显示当前上下文生成的首领和奖励。“查找团体战”从输入或随机选择的起始种子开始，在筛选条件允许的所有上下文中搜索（`pokeldn.sv.raid_search`），可筛选种类、星级、太晶属性、性格、性别、异色、体型证章和个体值范围。结果按首领能力值评分（HP 乘双防之和、HP 乘任一防御、较高攻击能力值或能力值总和），或按指定奖励数量排序（下文“所需奖励最多”）。不指定种类时，每种宝可梦只保留一个结果。

<a id="size-marks"></a>
### 体型证章

PKHeX 允许曾进入《朱／紫》、体型大小为 0 的宝可梦获得小不点之证，255 的获得大个子之证（`MarkRules.IsMarkAllowedMini`、`IsMarkAllowedJumbo`）。“可获得的体型证章”筛选要求首领体型为 0（小不点之证）、255（大个子之证），或两者之一（任意体型证章）。体型在身高、体重之后抽取（`boss_fields`）：

| 体型规则 | 体型大小 | 为 0 或 255 的概率 |
|---|---|---|
| 两次抽取（规则 0），所有普通和黑色结晶首领 | `next_int(0x81) + next_int(0x80)` | 各为 1 / 16 512 |
| 从 0 开始的活动区间（规则 1），或从 240 开始（规则 5） | `next_int(16) + low` | 所覆盖端点为 1 / 16 |
| 活动自身的固定值（规则 6） | 记录的 `scale` | 必定或不可能 |

`raid_search.size_marks` 给出所选活动结晶、星级、种类的首领可获得的证章，界面将其他选项置灰。

<a id="wanted-rewards"></a>
### 所需奖励

“奖励”区域默认折叠，展开后可指定道具及最低掉落数量。团体战中相同道具的数量会合并，两行相同道具的条件也会相加，结果会显示奖励。折叠后保留各行，但搜索忽略奖励条件。可选道具和数量来自搜索范围内可能掉落的奖励（`raid_search.reward_choices`）：对上下文中可抽取的每个遭遇（对应进度、版本的星级，或活动团体战地点），再按星级、种类和太晶属性缩小范围，取其固定奖励及随机奖励中该道具可能抽取的次数，上限为团体战的最大抽取次数；若随机表没有其他奖励，则必须抽满次数。首领可用的每种太晶属性决定碎片种类，种类决定宝可梦掉落物。一次列出全部帕底亚、北上乡、蓝莓学园上下文的 343 种道具约需一秒，因此列表在页面线程外生成。搜索跳过不可能满足奖励条件的遭遇，并先抽取种子奖励再生成首领。

“所需奖励最多”按指定奖励的顺序排序：先比较第一种道具的数量，再比较第二种，各行最低数量仍是必要条件。团体战中某道具的总量被视为一个数位，其值为该数量在搜索范围内所有可能总量中的升序位置（`raid_search.ranked_rewards`）：黑色结晶的宝可梦掉落物数量为 8 到 30，步长为 2，共 12 个位置。前几项道具的数位组成小于 2^31 的评分，辅助程序将其与种子共同保存为 64 位排序值；之后的道具仅检查最低数量。已知团体战至少可为五种道具排序（某活动的经验糖果 L 有 59 种总量，为道具中的最高值）；黑色结晶可为四种秘传调味料、特性膏药或王冠以及四种宝可梦掉落物排序。

<a id="the-helpers-scan"></a>
### 辅助程序扫描

PKHeX 辅助程序使用全部处理器核心扫描种子（`services/pkhex/RaidScan.cs`，由 `pokeldn.sv.raid_scan` 打包并发送到独立辅助进程）：生成种子遭遇、首领直至体型的字段、评分、全部筛选条件和奖励，等价于在上下文表上执行 `select`、`boss_fields`、`rewards` 和 `tera_type`。它返回上下文最佳种子（或各个种类的最佳种子），`search` 再用普通 Python 代码生成完整团体战，因此结果、顺序及种子和上下文的同分处理与 Python 扫描相同（`tests/test_sv_raid.py` 比较两者）。

扫描在生成遭遇后就排除大部分种子。每次请求先计算每条遭遇记录的最佳排序值：满个体值项为 31 并考虑所有可分配位置，其他个体值使用筛选允许的最佳值，性格使用其中最优值；按奖励排序时则使用各道具的最大掉落量。若种子对应记录不可能优于已有结果，就停止处理。通过后，在确定满个体值项和全部个体值后再次检查，依据任意性格下的最佳能力值评分（性格使能力值变化十分之一，评分随各项能力值增加）。按奖励排序时先抽取奖励，只查看掉落目标道具的随机奖励行；若剩余抽取次数也无法使第一项道具达到已有结果的首位数值，则停止。每次请求携带此前保留的排序值（每种宝可梦保留一个结果时按种类分别携带），仅首次请求携带上下文表，辅助程序按摘要缓存它们。

每次请求开始包含 16 777 216 个种子，之后调整为辅助程序约四分之一秒可扫描的数量，上限为 268 435 456。每个上下文最多搜索 4 294 967 296 个种子，上下文数量由所选范围决定（`most_seeds`）；界面默认提供一亿个种子，“搜索全部种子”遍历所有种子。“找到首个结果后停止”返回符合条件的首个团体战，不按评分择优（`stop_at_first`）：按顺序逐个搜索上下文，返回首个存在结果的上下文中最早的种子。没有辅助程序时（尚未构建它的源码目录），Python 约每秒扫描 22 000 个种子，上限为一百万组种子与上下文组合，界面默认提供 100 000 个种子。

Apple M4（10 核）上辅助程序预热后的测量结果：

| 搜索 | 时间 |
|---|---|
| 单个上下文的一千万个种子（朱、帕底亚、六星、普通结晶） | 0.02 秒；筛选异色时 0.03 秒 |
| 42 个上下文各一千万个种子 | 0.51 秒 |
| 42 个上下文各一亿个种子，即界面默认值 | 5.2 秒 |
| 单个上下文全部种子 | 6.1 秒 |
| 42 个上下文全部种子 | 4 分 3 秒 |
| 朱、帕底亚、黑色结晶的全部种子，先按两份秘传：苦味料再按两份特性膏药排序，每种宝可梦一个首领 | 20.9 秒 |
| 同一结晶全部种子，要求大个子之证 | 3.3 秒 |

<a id="the-battle-between-consoles"></a>
## 游戏机之间的对战

在两台模拟朱 4.0.0 之间测量，一台主持四星结晶，另一台从宝可入口站加入，两个空位为 NPC。主持游戏机整场保持会话。所有对战消息为键 0x007b 的战斗开始帧，地址 (0x2713, x, y)；32 字节头部 +0x00 为类型，+0x08 为 u64 步数，+0x10 为 u64 回合，+0x18 和 +0x19 为 5 及战斗者或站点字节：

| 类型 | 来源 | 大小 | 含义 |
| --- | --- | --- | --- |
| 0x01, 0x05, 0x11, 0x15, 0x25, 0x29, 0x47, 0x49 | 主机，地址 (0x2713, 1, 2) | 50 to 20626 | 步骤，加入方以相同计数器回复类型 + 1 |
| 0x02, 0x12, 0x16, 0x26, 0x2a, 0x48, 0x4a | 所有站点，地址 (0x2713, 3, 5) 或 (0x2713, 2, 2) | 50 | 步骤回应 |
| 0x06 | 站点发送自身战斗者指令；主机发送自身、各 NPC 及再次发送加入方指令 | 250 | 单个战斗者指令；+0x19 为席位（0 主机、2 加入方、3 和 4 NPC） |
| 0x15 | 主机，每个行动战斗者一条，包括首领 | 20626 | 回合：+0x20 包含五个 0x70 字节行动块（0 主机、1 首领、2 加入方、3 和 4 NPC）；+0x250 每席位一字节表示行动数量（[行动](#actions)），+0x258 为队列长度，+0x25c 起为队列；压缩后 123 至 802 字节 |
| 0x46 | 主机，开始时 62 次 | 54 |  |
| 0x51 | 主机 | 86 |  |

约四分钟内，加入方双向传输 475 条 0x80 端口 0 的可靠消息，线上共 27979 字节，单向每秒最多 80 条。仅主机发送 NPC 指令及类型 0x15 记录。

对战采用服务端、客户端结构。主机构建器 `0x113c8a0`（在 `0x113c908` 设置类型 0x15）复制行动块、执行回合（`0x113e3d0`），并附加产生的服务端命令队列。主机 AI 决定 NPC 指令，首领行动仅通过 0x15 到达加入方。加入方执行队列；对类型 0x13、0x15、0x17、0x19、0x1f、0x23、0x25、0x4d，还会使用同一构建器从主机行动块重建消息体，比较大小及字节（`0xf5cfa4`）。不一致则进入接收超时处理器 `0xf5bfd4`。主持对战的站点必须从相同状态生成与朱自身引擎完全相同的队列。

<a id="which-station-runs-the-server"></a>
### 运行对战服务端的站点

对战服务端是端口 2 成员列表第一项。所有游戏机根据大厅主机的 Session 类型 6（成员 `+0xa0`、代码 `+0xc0`、数量 `+0xc4`；构建器 `0xe457cc`）及类型 9 接收器 `0x18b68fc` 构建该列表；`pokeldn.sv.port2.build_session` 把主机排在首位。

| 步骤 | 代码 |
| --- | --- |
| 团体战开始 `0.4455`（Lua）把服务端席位设为 0：`setup:f4891D27C(0)` | `0x182ca10` -> `0x2d36398`, 设置 `+0x94` |
| 将成员 i 映射到席位 0、2、3、4，成员代码存入 `+0x99+slot`，自身代码对应席位存入 `+0x90` | `0x1ccd15c` 遍历端口 2 成员向量 `+0x170`; `0x2d363a0`, `0x130ea2c` |
| 开战时 `0x2a1cd74` 将设置 `+0x94` 复制到 `net+0x58`，`+0x90` 复制到 `net+0x5c`，仅执行一次 | 来自 `0x18915c4` |
| `!setup.710 && slot == net+0x58` 时游戏机为服务端 | net vf `+0x78` = `0x2a1d994`; 配置 `+0x2c` 通过 `0xfa363c`, 保存在服务端 `+0x490` |
| 0x15 检查器仅安装在非服务端游戏机 | `0xfb0ee8` |
| 超时或检查失败调用 net vf `+0x70` = `0x2a1d920`；团体战中设置 `net+0xca`，由 `0x18e217c` 将 `net+0x58` 设为自身席位（`net+0xf0`，在 `0x2a1cda8` 写入一次） | `0xf5bfd4` |

只有 `0x7faed0` 在构建字段 22 为真时，通过 Lua 绑定 `f3AF42713` 设置 `+0x710`；团体战开始不设置它。消息不直接指定服务端，成员顺序决定它。与服务端失联后，游戏机会将自己设为服务端直到对战结束，各台独立执行。排首位的大厅主机停止发送时，各台便独立对战。

成员向量仅追加，共三个写入来源，均经过 `0x18b65c8` → `0x18b68fc`：类型 6 或 7 的会话块（`0x18b566c`，首先追加项 `(block+0x98 code, block+0x90 host
station)`）、类型 6 成员重放（`0x279ba2c`）及类型 9（`0x1954bac`）。没有会话块前收到类型 9 会被丢弃（`0x18b65e4`）。每台的第 0 项均是首个会话块指定的主机。两台模拟朱 4.0.0 测得：

| 大厅主机发送内容 | 游戏机行为 |
| --- | --- |
| 类型 6 的块主机是接收游戏机本站点 | 不发送端口 2 加入，错误 7 |
| 大厅中，端口 2 类型 10（`0a b9 02 <slot> b9 01 <u64 station>`，解析器 `0x279bbdc`，删除器 `0x194562c`）指定块主机 | 离开会话 |
| 初始化数据后发送相同类型 10 | 提示“团体战已解散！” |
| 游戏机报告 320173（已加载）后发送相同类型 10 | 各自与两名 NPC 独立对战 |
| 成员代码指向空初始化参与者 | 对战加载中止（2162-0001） |
| 五个成员，第五个是游戏机（Lua 仅重映射索引 1 至 3，第五项映射到席位 0） | 大厅无成员；开始和初始化后，两台均在任何对战帧前离开 |

初始化参与者 k 属于代码 k 的成员。故障接管后，游戏机用自身 AI 控制其他全部战斗者：各席位读取器仅在开战时已是服务端的游戏机上创建（`0xfa52b0`、`0xfa5314`）。自身代码取成员向量中首个与本站点相同的项（`0xd5f3b4`）；Lua 席位循环（`0.4455` @1206..@1248）没有中途退出，因此最后一个匹配项决定本站席位。

<a id="the-battles-random-numbers"></a>
### 对战随机数

回合的所有随机抽取来自一个 0x28 字节的 xoroshiro128+ 对象（虚表 `0x4500bd0`）：

| 偏移 | 大小 | 含义 |
| --- | --- | --- |
| 0x00 | 8 | 虚表 |
| 0x08 | 2 x u64 | 状态 |
| 0x18 | u64 | 种子 |
| 0x20 | u64 | 抽取次数 |

服务端主模块为 0x378 字节，构造器 `0x12742d0`，在 `+0x10` 保存随机对象；回合代码通过 `[[x+0x10]+0x10]` 访问（`0x11440e8`）。初始化器 `0x127d824` 将状态设为种子和 `0x82A2B175229D6A5B`，计数设为 0（`0x127d9a8`），种子取自参数块 `+0x20`。加入方检查器从对战设置 `+0x718` 填入该值（`0x2891748`）；团体战开始脚本 `0.4455`（@1152..@1157）通过 Lua 绑定 `fAF4A81E0`（设置器 `0x7faf1c`）将 `+0x718` 设为 RaidPoint 的 `randSeed`。搭档种子同时也是对战种子，由写入初始化数据的站点选择。服务端创建的各席位模块（`0x126ba88`，由 `0xfa9f90` 调用）以种子 0 初始化。

模拟朱 4.0.0 参加以 `randSeed` `D64EB3974D89705E` 主持的团体战时，后续某回合服务端随机对象保留该种子，状态等于推进七步后的种子，计数 7；该回合抽取四次。

每次抽取求和 `s0 + s1` 并推进状态；计数每次调用加一，重新抽取不额外增加：

| 函数 | 抽取方式 |
| --- | --- |
| `0x11440f0(rand, n)` | 小于 n 的 u64：`s0 + s1` 按 n − 1 位数掩码，大于等于 n 则重抽；n 小于 2 时返回 0，不抽取 |
| `0x114da8c(rand, p)` | `(s0 + s1) & 0x7f` 大于等于 100 则重抽，小于 p 时为真 |

许多回合函数直接内联状态推进，不调用上述函数。

<a id="damage-and-draws-per-move"></a>
### 每次招式的伤害与随机抽取

以下结果测自随机宝可梦对抗普通团体战的参考程序对战（233 场，其中 29 场记录了每次抽取）。一次招式按以下顺序抽取随机数：

| 抽取 | 条件 | 决定内容 |
|---|---|---|
| `chance(25)` | 使用者处于麻痹状态 | 是否因麻痹无法行动 |
| `chance(accuracy)` | 招式具有命中率；100 仍会抽取 | 是否命中 |
| `below(24)`、`below(8)`、`below(2)` | 伤害招式，击中要害等级分别为 0、1、2 | 为 0 时击中要害 |
| `below(16)` | 伤害招式 | 伤害浮动 r：伤害乘以 (100 − r) / 100 |
| `chance(p)` | 概率为 p 的追加效果（如泰山压顶的 30） | 是否触发效果 |

对首领的畏缩追加效果不抽取随机数（规则见[回合队列中的招式](#a-move-in-the-round-queue)）。100% 降低能力的追加效果（灵魂冲击、重踏）在部分回合抽取 `chance(0)`，其他回合不抽取。两名战斗者速度相同时，首个招式前抽取 `below(2)`。

每场对战在首回合前抽取一次 `below(100)`。伤害采用 Showdown 的第九世代公式（数据来自 Pokémon Showdown 的 `moves.json` 和 `typechart`），使用队伍记录中的能力值，首领防守属性仅取太晶属性：能力等级变化前对首领的 1346 次命中中，921 次符合该公式；记录全部随机抽取的 140 次命中中，137 次可由记录的伤害浮动和要害抽取还原伤害。不符合的命中发生在首领护盾期间（约为公式结果的 0.45），或使用特殊规则招式（扑击、电力上升、连续攻击招式），或伤害被剩余 HP 截断。

首领的 HP 池为记录中的 HP 乘以 RaidPoint 的 HP 系数再除以 100（[对战引导数据](#the-battle-bootstrap)）：获胜的参考程序对战中，一至四星分别有 78、84、125、35 场在 `0x37 (2, 2, damage)` 累计恰好扣除记录 HP 的 5、5、8、12 倍后结束；其他场次因护盾和特殊规则招式而更少。

<a id="a-move-in-the-round-queue"></a>
### 回合队列中的招式

每个战斗者的招式在回合队列中是一段连续命令。战斗者 1、3、4、5 的客户端位置为 0 至 3，首领为 4；A 是使用者，T 是目标，M 是招式，`type` 为招式属性索引，`cat` 为分类（1 物理、2 特殊）。以下测自玩家命中首领、首领回击玩家的参考程序回合：

| 命令 | 含义 |
|---|---|
| `0x05 (A, 0, pp)` | 玩家招式开始，消耗 pp（目标有压迫感时为 2，否则为 1）；首领没有此命令 |
| `0x07 (A, 0)` | 使用招式 |
| `0xc9 (A, 0, M, T's position, 0)` | 招式及目标 |
| `0x7b (M, n, A)` | n 为此前的回合数 |
| 六组全零 `0xcf` | 分别为 20、5、5、5、19、20 字节 |
| `0x7e (0, ...)`、`0x7e (1, 0, 0, 0, 0, 0)`、`0x7e (2, e, e, e, e, e)` | 第一条在 T 的位置 + 1 处为 1；第三条为各位置的属性效果码，无效果为 7 |
| `0x8b (A's position, T's position, M, type, 0, 0, 1, tera, 0, 0)` | 命中；首领使用与太晶属性相同的伤害招式时 `tera` 为 1（448 次均如此），否则为 0 |
| `0x37 (T, 2, damage)`、`0x37 (T, 5, 1)`、`0x02 (T, A, damage, 3)` | 伤害 |
| 字节为 `T, e` 的 `0xd0` | e 为属性效果：7 普通、6 效果不好、8 效果绝佳 |
| `0x8e (1, 1, M)`；效果不好时 `0x8e (1, 3, M)` 与 `0xca (A, 575, 0xffff0000)`；效果绝佳时 `0x8e (1, 2, M)` 与 `0xca (A, 574, 0xffff0000)` | 属性效果消息 |
| `0x20 (A, 24)` | 仅效果绝佳的命中 |
| `0x42 (T, A, A's position, type, cat, M, damage)` | 命中记录 |
| 招式可吸取 HP 且使用者未满 HP 时的吸取 | `0xa7 (T, 51)`、`0x03 (A, heal)`、`0x9a (A, heal)`、`0xcb (A, 290, T)`；恢复量为伤害乘以吸取比例，四舍五入，最多恢复使用者缺少的 HP |
| 追加效果（如有） | 例如麻痹：`0x13`、`0x90`、`0xa7`、`0xcb (2, 92, T)` |
| 字节为 `01 00` 的 `0xd1`、`0x2e (2, A − 1)` | |
| `0x85 (7, damage)` | 仅对首领造成伤害时 |
| `0x7c ()`、`0x08 (A, 0)`、`0x1d (A, T's position, type, 1, 0, M, M)`、两次 `0x5b (A, M)`、`0x1e (A, 0)` | 招式结束 |

回合结尾依次为 `0xb2 (0)`、对每位行动战斗者发送 `0x37 (b, 7, 1)`、`0x75 (3, n)`、`0xc5 (1)`，再按速度顺序（队伍记录中的速度，首领也在其中）对每名战斗者发送 `0x43 (b)`，按 ID 顺序对本回合行动者（首回合为全部五位）发送 `0x23 (b)`，最后为 `0x2d (0)`；`0x75 (3, n)` 计数包含本回合。

击倒首领的命中会赢得对战。其 `0x42` 后依次为 `0x49 (2, A, M)`、`0x09 (A, 0)`、`0x37 (2, 1, 1)`、`0xcb (2, 0, 2)`、`0x94 (2, 0)`、`0x37 (2, 8, 1)`、`0x5f (2)`、`0x62 (2)`、`0x6c (2)`、`0x5d (2)`，按 ID 顺序为每名玩家发送 `0x41 (b, 2)`，k 从 0 至 13 但跳过 8 的 `0x33 (2, k)`，以及 `0x80 (2)`、`0x29 (2)`、`0x38 (A)`，随后为正常招式结尾。之后无人再行动；回合结尾仅包含仍站立战斗者的 `0x43`、`0x23` 列表和 `0x2d (0)`。`0x85 (7, damage)` 与伤害命令携带的是首领剩余 HP。

前缀从 `0xb5 (0)` 开始，先按 ID 顺序、再按行动顺序，对本回合行动者各运行一次 `0x51 (b, 1)`；第二轮中有慢出（特性 100）的战斗者最后行动，并携带 `0x51 (b, 0)`。所选招式会注册处理函数的战斗者，在每轮后按该轮顺序追加 `0x5a (b, M, speed)` 和 `0x5b (b, M)`，随后再按行动顺序追加两轮。首位之后的每名战斗者行动前，这些战斗者再重复该命令对一次；招式注册处理函数的行动者还会在自身 `0x05` 前添加 `0x5a (b, M, 0x72000 + speed)`。通过在参考程序对战中使用每个招式并观察 `0x5a` 判定注册情况：631 个使用过的招式中有 347 个会注册（包括硬撑、泰山压顶，不包括暗袭要害）。

首领从开始就处于太晶化状态：与其太晶属性相同、威力低于 60、没有先制优先度且单次命中的伤害招式，按第九世代太晶规则以威力 60 命中（一般太晶的迷你芙使用撞击造成 4 点伤害，威力 40 仅会造成 2 点）。追加效果按 Showdown 顺序分别抽取 `chance(n)`，但对首领的畏缩不抽取：玩家的冰冻牙只抽取冰冻概率（冰冻显示为 `0x13 (2, 3, 0, 1, 4)` 及消息 97、98，首领行动前抽取 `chance(20)` 判定解冻），首领对玩家使用冰冻牙则两项都抽取。击倒首领的命中会先抽取 `chance(0)`，无论有无追加效果。

按上述规则、Showdown 招式数据和第九世代伤害公式构建，554 场参考程序对战的首回合中有 56 场逐字节一致，没有出现不一致，其余均因包含不支持情形而拒绝。从开始正文连续运行到首领被击倒，有 20 场完整对战的每回合均与参考程序一致。对同一脚本游戏机端到端提供服务时，双方均成功运行的 19 场对战中，每一帧都在相同帧时刻、按相同顺序发送（第 20 场参考程序服务器失败）。

以下回合会被拒绝：行动或受击的战斗者持有其 Showdown 回调可能改变回合的特性或道具（如活力影响攻击、斗争心影响威力、友情防守的 0.75 倍、胆怯在恶属性命中后提高速度、疾风之翼影响优先度），除非样本已测得该特性或道具在此处不生效；或对战含有入场时生效的特性（如威吓在首回合前降低攻击）。

<a id="actions"></a>
### 行动

回合行动头部（请求块，0x238 字节）由五个 0x70 字节块组成，每个客户端席位一块；每块最多七条 16 字节行动，分别为一个 u64 行动字、一个 u32 执行者战斗 ID，以及没有代码写入的 4 字节。+0x230 为每个席位提供一个字节，计数该块的行动数量。服务器按席位顺序解码为 0x8c 字节行动项（`0x1145e40`，解码器 `0x11461b4`）。行动字的低四位为类型：

| 类型 | 条目类型 | 行动字字段 |
|---|---|---|
| 1 | 1, 招式 | 位 4..7 目标对战位置, 8..23 招式, 位 25 标志 |
| 2 | 2 | 位 4..19 和 20..27; 后接 u32 |
| 3 | 3, 替换宝可梦 | 位 4..7 同行队伍位置（执行者为该成员）, 8..11, 位 12 |
| 4 | 6 | 位 4..11, 12..15 和 16..23 |
| 5 | 4 | 位 4 |
| 6 | 5 | 位 4..11 |
| 7, 10, 11 | 7, 8, 9 | 无 |
| 9 | 10 | 位 4..11 |
| 12 | 11 | 位 4..11; 后接 u32 |
| 13 | 14 | 位 4..7, 8..11, 12..15, 16..27, 32..43, 44..55, 56..59, 60..63 |

位 0..3 为 3 且位 12 已设置的行动字跳过，类型 0、8、14、15 也跳过。记录的玩家行动 `41 67 03 00 ...` 为招式（类型 1），目标位置 4，招式 871（闪焰高歌）。

团体战的战斗者 ID：1 为位置 0 的宝可梦，2 为首领，3 对应位置 2，4 对应位置 3，5 对应位置 4。站点的类型 0x06 命令共 0xe8 字节：0x20 字节头部（+0x19 是席位），+0x20 为计数字节，+0x28 起为 (u64 行动字、u64 执行者) 对。命令携带本席位的行动及首领对该席位的回应：加入方对位置 2 的命令包含 `move 871 at position 4 by battler 3` 及 `move 204 at position 1
by battler 2`。各站点选择首领针对自身宝可梦使用的招式。

服务器为每个行动席位填入一个回合请求块：

| 步骤 | 代码 |
|---|---|
| 提交方栈上的 0x240 字节块：每条行动的行动字与执行者清零，计数清零，+0x238 为类型 0x15 | 各席位读取器步骤 `0xf6df44` 中的 `0xf6e6a8`；其他类型使用 `0xf71d10` |
| 复制该席位的类型 6 消息（reader +0x30 为存储，u32 +0x38 为席位）：清零计数字节，追加每对的 u64 行动字和执行者低 u32，递增计数；无边界检查，超过 7 会写入下一席位 | `0xf702ec` → `0xf7065c`（键 6、0xe8 字节消息）；键 0x10 进入 `0xf72038`（单条行动的 0x30 字节消息，仅在席位最多已有六条行动时接收） |
| 将 0x240 字节作为类型散列 `0xae1b39fccfd09053` 的任务提交 | `0xf6ffb8`，任务类虚函数表 `0x4494198`（构造函数 `0x17b52a4` 将 0x240 字节复制到 job +0x78） |
| 任务将块复制到服务器对象 +0x210（构建器的 [o+0x40]） | `0x16e4f84` → `0x113bac0` |
| 递增步骤计数器 +0x198；若已收到该步骤的消息体（`0xe63734` 检查 [[server+0x448]+0x38] 的双端队列），直接替代构建；否则以类型 0x15 调用构建器 | `0x113bad8` → `0x113c8a0` |

因此，一个回合块只包含一个席位的行动。每条行动未写入的 4 字节，以及 0x235..0x237 字节，来自提交方栈，并原样进入类型 0x15 消息体；回合不读取这些字节。在两台模拟《朱》4.0.0 之间，除上述字节外，每份类型 0x15 记录都等于用其行动席位的类型 6 命令构建的块：线上可见命令的 10 份记录全部匹配。首领自己的位置 1 块没有此命令，见[首领的行动](#the-bosss-actions)。四场模拟会话的回合仅从行动运行，得到的 20576 字节消息体，除上述字节外均与游戏机相同。

<a id="the-battle-start-body"></a>
### 对战开始正文

消息 0x11 正文是没有长度字的命令队列（[服务端命令队列](#the-server-command-queue)）。战斗者 ID：槽位 0 为 1，首领（槽位 1）为 2，槽位 2 为 3，槽位 3、4 为 4、5；位置为 ID − 1。正文按 ID 顺序派出战斗者，再执行入场事件，最后为 `0x2b (0)`：

| 命令 | 含义 |
|---|---|

### 首领的行动

首领的额外行动保存在最多四项的列表中：u8 类型位于 +0x5c + 8i，u32 值位于 +0x60 + 8i，计数位于 +0x7c；+0x10 起先存放 RaidPoint 行动配置的副本。回合引擎的列表为 `[module+0x1b0]`（`0x16e5c90`），每回合重置；服务器逐帧状态机另有自己的列表。

| 类型 | 入队条件 | 值 |
|---|---|---|
| 1 | 护盾（`0xf6f87c`）：开始前，剩余时间不高于配置 +0x14 的百分比，或 HP 不高于 +0x12 | 时间触发时为计时器的 `0xf70af0`，HP 触发时为 0 |
| 2 | 护盾结束（`0xf6f87c`，`0xf70010` 对照 +0x18） | 1 |
| 3 | `0xf6dd84` 的时间检查发现剩余时间不超过 10% | 1 |
| 4 | 六种额外行动（`0xf6fa5c`：+0x24 + 8i 保存类型、时机 1 时间 / 2 HP、阈值、招式），每项一次（记录 +0x86 + i） | 行动索引 |
| 5 | 双重行动（`0xf6de7c`）：HP 不高于配置 +0x54 | 0 |

这些行动都不抽取随机数；触发条件仅为首领 HP 比例或剩余时间阈值（对战计时器的 `0xf91070`）。作为请求块行动时（`0x114fb2c`），行动字的类型为 12，位 4..11 是列表类型，位 32..47 是值，执行者为团体战战斗者 ID（`0x114fc70`）。

回合期间，空列表由 HP 触发条件填入（`0x11425b0`）；若没有护盾行动，则在该回合运行这些行动（`0x1145be0`）。回合之后，结果字节 `0xc4a5` 选择下一步骤；ServerCommand（`0x16e4f6c`）在构建器的 `0xc4a4` 设置时改为传入 8，团体战行动则原样传递该字节（`0x16e4ff0`，跳转表 `0x3c61c38`）：0 无操作、4 空回合（`0x16e5cac`）、6 包含护盾的回合列表（`0x16e5ad0`）、7 结束对战（[对战结束](#the-battles-end)）。团体战行动（`0x18c92a8`，载荷由 `0x17b5f3c` 复制）有四种状态：

| 状态 | 服务器行为 |
|---|---|
| 0 | 向所有站点发送消息 0x47；以原因 0 暂停对战计时器（`0x18c9a68`） |
| 1 | 等待每个已入座席位发送该步骤的消息（`0xe63380`） |
| 2 | 在请求块的位置 1 放入行动（计数字节 +0x231）；以原因 0 恢复对战计时器（`0xe63ac4`）；将块作为回合 0x15 发送 |
| 3 | 按回合结果进入下一步骤，清空列表（`0xfaf024`），删除各席位的 0x47 及回应 0x48 |

不含护盾的列表从状态 2 开始。首领列表为空时，逐帧状态机在列表副本上检查配置的时间触发条件（`0xf6d62c`）；触发后将副本作为消息 0x51 发送（`0xf71b74`）。0x51 经服务器自身席位返回状态机并填入其列表（[服务器流程](#the-servers-flow)）；状态机列表有行动时，提交团体战行动（`0xf6d8d4`）。

两台模拟《朱》4.0.0 之间，一只四星首领的配置为：剩余时间 80% 时使用行动 3 大晴天，HP 75% 时行动 1，HP 40% 时行动 2，HP 50% 或剩余时间 30% 时展开护盾。它产生三个位置 1 回合：先只有类型 4、值 0（无 0x47，同时发送 0x51），随后加入方攻击后发送 0x47，以及类型 1 和类型 4、值 2，再次发送 0x47 和类型 1。HP 75% 的行动在越过阈值的位置 0 回合内部执行。

### 对战计时器

对战计时器是位于服务器上下文 +0x38 的 0x28 字节对象；该上下文由逐帧状态机和各任务的 `[+0x40]` 指向，同时在 +8 持有 N、+0x10 持有服务器模块、+0x18 持有服务器：

| 偏移 | 字段 |
|---|---|
| +0x00 | u64 开始时间，单位为 `nn::os::GetSystemTick` 的纳秒；暂停时为 0 |
| +0x08 | u64 上次暂停之前累计运行的纳秒数 |
| +0x10 | u64 上次暂停时间 |
| +0x18 | u8 是否已开始 |
| +0x19, +0x1a | u8 暂停原因；两者均为 0 时计时器运行 |
| +0x20 | 创建时的时间限制 |

| 事件 | 代码 |
|---|---|
| 对战第一个任务创建并启动计时器，立即以原因 0 暂停；仅在限制 N+0x8a 非零时执行 | `0xf70864`、`0xf70a58` |
| Wild::Setup 结束时以原因 0 恢复；未开始的计时器在此开始 | `0x2a1fbfc`，`0xe63a6c` 的步骤 |
| 从团体战行动消息 0x47 到其回合之间，以原因 0 暂停 | `0x18c9a68`、`0xe63ac4` |
| 读取：限制加 `[[module+0x1b0]+8]` 的 i16，减去本次开始后运行的整秒数及累计整秒数；暂停时为限制减累计秒数；零限制返回 1 | `0xf91070` |

逐帧状态机仅在计时器已开始（+0x18），且设置 +0x499 的位 2 设置时检查时间触发条件（`0xf6d538`）。剩余时间百分比按整数除法计算 100 × 剩余时间 / 限制，不高于阈值 P 时触发：300 秒计时器的 80% 触发点为剩余 242 秒，即已运行 58 秒。在下述服务端对战中，最后一个站点对消息 0x11 的回应到达服务器时开始计时，80% 行动在 58.1 秒后发出。

### 对战计时耗尽

每个运行帧的开头，逐帧状态机（`0xf6d538`）使用限制 N+0x8a 和 [[module+0x1b0]+8] 的 i16 读取对战计时器（`0xf91070`）。有符号结果不大于 0 时，在首领列表与读取器之前进入超时分支 `0xf6d830`：

| 步骤 | 代码 |
|---|---|
| N 尚无结果时，保存结果 0、N+0x94 = 2；不强制覆盖已有结果 | `0xe7d570(N, 0, 2, 0)` |
| server+0x208 的 0x29 消息体：N 自身席位、结果（`0x166882c`）、N+0x94 | `0xe7d4c8` |
| 设置 +0x499 的位 2 设置（团体战）时，提交消息为 0x2b 的 ExitBattleEnd | `0x201602c`（散列 `0x2da7b4584624a364`，构造函数 `0x1882dbc` 将消息保存在 +0x78） |
| 其他情况：提交类型 0 的 AddExpBattleEnd | `0x16e5230`（散列 `0x23607a0597b3a656`） |

状态机只在没有任务运行时执行，因此回合或团体战行动期间计时耗尽，要等该任务结束才会发现。ExitBattleEnd 向所有站点发送 0x2b 并等待所有回应；0x2b 不等于 0x29，因此不接 RaidCapture，淡出依次发送 0x35、0x37（[对战结束](#the-battles-end)）。团体战超时时不发送 0x25。

下述 rme10 会话中，先使用直到 416.5 秒的录制消息，再由站点在 0.1 秒后回应除 5、0x37 外的所有奇数消息，不发送命令；以每次 10 秒将时钟推进到 700 秒。unicorn 中的游戏服务器代码与 `Server` 向每个席位发送的消息顺序及内容相同，不比较未写入字节：先是首领最后一个定时行动的回合（类型 3，剩余时间 10%），随后为消息体 `00 00 00 00 02 00` 的 0x2b（席位 0、结果 0、判定方式 2）、0x35、0x37。

首领获胜的团体战以相同方式结束。在同一会话从 414.5 秒开始，站点对每个请求提交命令：自己的宝可梦对首领使用叫声（招式 45），首领以招式 0x1cc 回应该宝可梦。游戏服务器代码和 `Server` 向各席位发送相同顺序的 1311 条消息。玩家宝可梦每次濒死，从 300 秒计时中扣除 75 秒（[[module+0x1b0]+8] 的 i16 依次降为 -75、-150，并在 439.7 秒降为 -225）；到 -225 时，超时分支发送 0x2b（席位 0、结果 0、判定方式 2）、0x35、0x37。宝可梦濒死的席位进入读取器子状态（[服务器流程](#the-servers-flow)）：

| 消息 | 目标 | 内容 |
|---|---|---|
| 0x21 | 仅濒死席位，只有头部 | 席位没有可战斗成员时发送；回应 0x22 启动读取器计时器（reader+0x50，限制由 `0x1ffe4e8` 读取） |

<a id="the-servers-flow"></a>
### 服务器流程

游戏机上，各步骤以任务形式运行：先是 Wild::Setup，随后是 ServerRequest（`0x138d178`，向一个席位发送消息 5）、ServerCommand（`0x16e4f10`，把提交的请求块作为回合运行，再按结果进入下一步骤）、RaidAction 及对战结束。Wild::Setup（`0x2a1f54c`，十一种状态，跳转表 `0x3c61c1e`）发送消息 1，等待所有席位回应，再发送 0x11（设置类型 4 改走 `0x2017ba4`；团体战设置 +0x30 为类型 0，即获胜时发送 0x29 的类型，录制中的 0x29 可确认），等待全部回应，清除各入座席位发送内容（`0xe0f5f8`）。0x11 结果字节为 1 时发送消息 3，收到回应后发送 0x13；该字节是开始标志 [[o+0x40]+0x28]，只有 `0x2840fac` 将其设为 1，经 `0x2840f70` 从七处调用（`0x284b710`、`0x284b8f0`、`0x285c5d0`、`0x286d480`、`0x286d784`、`0x286d9b0`、`0x28780f8`）；实测团体战开始均未设置它。随后删除各席位的 3、4 并启动对战计时器。逐帧状态机（`0xf6d538`）推进五个按席位分配的读取器（`0xf6df44`）及首领列表。与服务器同阵营的玩家席位读取器如下：

| 读取器状态 | 条件 | 后续行为 |
|---|---|---|
| 0 | 席位发送条目不含 5、0xd、0xb、0xf、9、7、0x21、3、0x23、0x15、0x17、0x19、0x13、0x47、0x1f、0x1d | 为席位创建 ServerRequest（`0xf70078`），进入状态 1 |
| 0 | 其他情况 | 从两个条目中删除已回应的消息对（`0xf6edf4` 处理 0x15/0x16、0x23/0x24、0x11/0x12、0x13/0x14、0x17/0x18、0x19/0x1a、0x1b/0x1c、0x1d/0x1e、0x25/0x26、0x1f/0x20） |
| 1 | 已向席位发送 5，且收到 6 | 清零块并收集席位命令（`0xf6e6a8`、`0xf702ec` 键 6，完成键 5），作为 ServerCommand 提交，进入状态 2 |
| 2 | 席位已回应回合（0x15 / 0x16） | 返回状态 0 |

席位是否属于首领阵营，由表 `0x3c6a45a`（0, 1, 0, 0, 0）相对 N+0x95 决定；首领阵营读取器只删除已回应消息对。读取器（`0xf6df44`..`0xf6edf0`）还有表外路径：席位发送 4 时，以类型 0x13 块回应；团体战中 N 的同阵营席位运行 reader+9 的子状态：0 通过散列 `0x935acb1823e1803f` 的 8 字节请求向席位发送 {slot, 0x21}（`0xf6f6d8`）；3 在 reader+0x50 创建计时器，限制由 `0x1ffe4e8` 从表 `0x3c69d1c` 读取；1 在计时器耗尽后提交类型 0x23 块（`0x2016bc8`）；2 等待 0x23/0x24。0xd/0xe 提交类型 0x1b 块；若 0xe 消息体首字节为 0，则提交请求 {slot, 7}。7/8、0xb/0xc、0xf/0x10 及收到的 0xa 分别提交类型 0x17、0x19、0x15、0x17 块。提交块在类型后面的 +0x23c..+0x23f 字节来自栈。

每帧，团体战运行步骤 `0x2d383b8(N)` 在 `0x2d38694` 推进服务器接收链接（`0xe0f040`、`0xe0fd68`、`0xe0f854`，作用于 [N+0xb0]），再运行任务图 `0xfc363c(G, 1)`，G = [N+0xa8]（0xe8 字节，虚函数表 `0x44ee6e8`；其 +0x40 为任务上下文，虚函数表 `0x44ee808`）：

| G+ | 对象 | 内容 |
|---|---|---|
| 0x98 | 请求工厂（0x48 字节） | 提交的请求为 0x50 字节消息对象，包含任务类型散列、计数器及任务载荷 |
| 0xa0 | 调度器（0x78 字节，虚函数表 `0x44eea68`） | +0x40..+0x50 的向量保存已提交请求，由 `0x1479b10` 追加 |
| 0xa8 | 来源对象（虚函数表 `0x44947d8`） | vf 0x68 `0x14641ec` 选择要启动的请求 |
| 0xb0 | 逐帧状态机（虚函数表 `0x4493530`，由 `0x17e1c5c` 创建） | vf 0x68 `0xf6d538`；+0x40 为上下文、+0x48 为工厂、+0x50 为调度器 |
| 0xb8 | 执行器（虚函数表 `0x4493688`） | 任务栈，使用双端队列，计数位于 +0xa0 |

`0xfc363c(G, 1)` 在执行器有任务时仅运行执行器。执行器为空时，先运行状态机，再由来源对象选择：团体战（设置 +0x498 位 0x400）优先选首个散列 `0x5c307d44ea569b63` 的请求（团体战行动，`0xf71928`）；模块开始标志 [[module+0x1f0]+8] 未设置时，选首个散列 `0x2e9e7a3009002c36` 的请求（Wild::Setup，`0xf7093c`）；其他情况选首个已提交请求。选定请求离开调度器（`0xfc3f58`），执行器 vf 0x68 `0x17b410c` 按散列创建任务并压栈，随后运行执行器。执行器（`0xfc38dc`）执行栈顶任务 vf 0x68：返回 0 结束该帧；返回 2 弹出任务，有后续任务 [job+0x70] 时将其压栈，再结束该帧；其他返回值则再次运行栈顶任务。因此状态机及读取器只在没有任务的帧中运行，每帧启动一个提交请求，团体战行动会优先于先前提交的其他请求。这解释了捕获中团体战行动后，三个命令作为回合发送的顺序。

状态机的定时检查将首领列表副本作为消息 0x51（`0xf71b74`）发入服务器自身席位的接收链接（`0xe0f440(server, N+0x95)`、`0xf71980`）。下一帧，接收链接步骤将其交给状态机 vf 0x78 `0x2016290`，复制 0x24 字节到状态机首领列表 [+0xf8]+0x5c，随后状态机从此提交团体战行动。vf 0x70 `0x20162bc` 还接收另外两种消息，由其 +0x40 的 u64 区分：`0x0ab4bce035f3012b`（0x2588 字节载荷，以 `0x201665c` 的任务提交）和 `0xde3856ecc4fe200c`（包含一条类型 14 行动的请求块，以 ServerCommand 提交）。

在引擎构建的会话上，通过 unicorn 运行《朱》自身服务器代码（`scratchpad/battle/timeup/gameserve.py`：每秒 30 帧调用 `0x2d383b8`，按中继顺序和捕获时间输入站点消息），向加入方发送的 24 帧均与游戏机一致，不比较头部及请求块中未写入的字节。没有接收链接步骤时，0x51 副本无法到达首领列表，80% 行动也永不触发。

`Server` 在引擎构建的会话上运行这一流程：每帧执行运行步骤的服务器部分（`0xe0f040`、`0xe0fd68`、`0xe0f854`、`0xfc363c(G, 1)`，步骤移动时还包括 `0x2898350`）。此流程已有 Python 移植。按状态机时钟每秒 30 帧，运行到每条输入消息的时间，并在其后再运行一个帧周期。不能将任何帧视为空闲而跳过：等待濒死席位计时器的读取器会使状态机每帧报告移动，每帧都向服务器自身链接排入消息 0x46。通过 unicorn 对照全部 216 个已移植函数，录制对战、超时、获胜结束及首领获胜对战的每个事件后，内存页均与游戏原代码一致。

主机将服务器收到的所有消息，包括本地客户端和加入方消息，经同一个队列中继给加入方（地址 x 3，每帧间隔 0.05 至 0.15 秒，也包括加入方自己的消息）。因此队列顺序就是服务器读取顺序：加入方比本地客户端早 0.5 秒发送的回应，仍可能晚到服务器。从模拟主机自身初始化消息（捕获中的 0x2f），按中继顺序和状态机时钟捕获时间输入各站点消息，服务器会按相同顺序向加入方发送游戏机的全部 24 帧：类型 1、0x11、四个请求、13 个回合（含首领三个回合）、两个 0x47，再接 0x25、0x29、0x49。除头部及请求块未写入字节（[行动](#actions)）外，每帧与游戏机逐字节相同；首领定时行动从计时器自身起点出发，在与游戏机相同的帧触发。在 unicorn 中，游戏自身每个已移植步骤在整场服务端对战中留下相同内存页。

<a id="reproducing-a-round"></a>
### 复现回合

在模拟游戏机停在类型 0x15 构建器 `0x113c8a0` 时，可用 unicorn 精确重放回合。首次访问页面时从 GDB 桩逐页读取内存；`tpidrro_el0` 后的线程本地页为替代页，`+0x1f8` 指向模拟线程；SVC 0x10、0x11、0x12、0x1a、0x1b、0x1d、0x1e 返回 0。十一轮重放结果与游戏机随后自行构建的消息体逐字节相同；每回合访问 159 至 353 页。

服务器的 Python 移植，每个游戏函数对应一个 Python 函数，以相对 main 的偏移为键。消息类型 1、5、17、21 的构建器 `0x113c8a0` 在 Python 中运行，包括回合驱动 `0x113e3d0` 及其招式选择、伤害 `0xf7c344`、濒死 `0x1144df8`、回合结束 `0x114a094`，以及对战开始 `0x113dca8` 的出场、道具、特性与入场处理程序。在 86 次暂停游戏机的检查中（49 个回合、5 次对战开始），移植代码留下的消息体及内存页与游戏原代码相同，没有将调用交回游戏。堆使用基于线程缓存的 SDK `nn::mem::StandardAllocator`，已连同缓存创建及其 TinyMT32 密钥（`0x525f448`）移植。对战状态构建步骤 `0x2891748`、`0x2892ac0`、`0x2d381a4` 和 `0x2892dd4` 也已包含入口在内完整运行于 Python，留下与游戏相同的内存页。保护变量的字节 0 和字节 1 均未设置时，`__cxa_guard_acquire`（`0x53c49a0`）返回 1，并将保护变量字节 1 设为 2。

一个使用祸不单行的回合读取自身未写入的 16838 字节：静态映像 1496 字节，命令格式映射 5372 字节、服务器对象 2926 字节（均由 `0x2d381a4` 创建），战斗者及其宝可梦 2414 字节（由 `0x2892ac0` 创建），主模块函数族 1756 字节（由 `0x2891748` 创建），数据表 2278 字节，回合行动块 576 字节。

数据表是由函数局部静态变量持有的 romfs 文件：

| 静态变量 | 文件 | 对象 |
|---|---|---|
| `0x47420b8` | `avalon/data/personal_array.bin` | 映射，键为种类编号 * 10000 + 形态（u32） |
| `0x47420d8` | `avalon/data/growTable.bin` | FlatBuffers 根，通过 [T+0x30] 的 vf +0x70 访问 |
| `0x4742568` | `avalon/data/waza_array.bin` | 映射，键为招式编号（u16） |
| `0x4742548` | `avalon/data/tokusei_array.bin` | 映射，键为特性编号（u16） |
| `0x4734e50` | `world/data/battle/battle_item_conversion/battle_item_conversion_array.bin` | 数组 |

映射是位于 +0x68 的 libc++ `unordered_map`：桶位于 +0x68，桶数位于 +0x70（不小于记录数的下一个质数），首节点 +0x98，大小 +0xc0，装载因子 +0xc8（1.0），默认记录 +0xd0（键 0 对应的记录）。节点为 {后继、散列 = 键、键、指向已加载文件内记录的指针}；+0x30 为文件资源（FNV 散列 +0x48、路径 +0x50）。道具数组由 `0x1821674` 填入，从 +0x28 起为 0x18 字节条目：u32 索引、u32 0、u64 散列、u16 道具、六个零字节。条目 i 对应文件记录 i，散列取自 main `0x3c61260 + 8 * index` 的 u64。文件来自 `arc/data.trpfs`（`tools/switch/trpfs_read.py`；Oodle 条目通过游戏自身 `0xcc8750` 的 `OodleLZ_Decompress` 解压）；97 次暂停游戏机时持有的文件逐字节等于提取文件。

对战开始也能在没有暂停游戏机的情况下运行。仅使用静态映像和 romfs，移植代码构建游戏堆、“Application”计数分配器（`0x3b78d3d`，上限 0xa0000000，基于 GlobalHeap 分配器 0x4763918）、弱句柄表（`0x165dd08`）及五张数据表（种族表 `0x164498c`、ID 散列表 `0x1730f6c`）。随后，使用游戏自身创建函数生成会话及服务器对象 N，将初始化消息中的团体战开始字段填入设置。N 的开始状态运行四个构建步骤，再运行类型 0x11 构建器。五场会话的对战开始消息体（268、345、328、422、268 字节）均与游戏机一致；九个后续回合的 20576 字节消息体也一致，每回合由行动席位的两条行动构建（[行动](#actions)），不比较请求块中未写入的栈字节。改变对战种子不影响开始消息体，但会改变回合的 123 字节。堆地址及弱句柄 ID 都不会进入消息体：游戏机的 ID 是第 3 代的 0x1b5xx，而移植代码为 0..0x58，所有对象也位于不同地址。

团体战开始通过 Lua（0.4455 → 0.4893 → 0.4945）调用绑定写入设置。四台游戏机的下列字段一致：u32 +0x2c 10003（`fD8E195CA`，即构建器在 [N+0x110]+0x40 读取的 0x2713），u32 +0x34 模式 2，+0x8c 1，+0x8d 规则 5，u32 +0x90 游戏机席位 2，u32 +0x94 服务器席位 0，+0x99.. 的成员代码 (0, 0xff, 1, 0xff, 0xff)，+0x488 与 +0x489 均为 1，+0x498 0x400，u32 +0x4b0 12000，u32 +0x4b4 400，+0x4dd 与 +0x4df 均为 1，u32 +0x4ec 0，+0x706 1，+0x714 8；每个参与者从 +0x18 起还有六个 0x1c 字节条目，u16 +0x10 为 30（首领为 26），u8 +0xd 为 1（主持方条目 1 至 5，加入方 0 至 5）。初始化消息提供种子（+0x718）、时间限制（+0x48a、+0x48c、+0x48e）、首领行动配置（+0x514）及队伍持有对象（+0xa0..）。在 unicorn 中，游戏自身代码从这些字段生成的管理器、S、N+0x48、N 及状态 0 写入，与移植代码一致，不比较游戏从栈填充复制的字节。

四部分仍在外部：S 的任务（`0x159f018`，其构造函数需要引擎任务调度器，对战代码不读取 S+0x40），任务图链接（`0x1193e44`、`0x11fd13c`），资源系统（setup+0x720 经 `0x1ffbb68`，加载器 N+0x1a8 经 `0x1802edc` 和 `0x1929dc4`，状态 1 等待它），以及为选举对象提供站点 ID 的 Pia 网络管理器 `[[0x46d6ca0]]`。

数据系统初始化 `0x1641afc` 运行 `0x1643a48`（种族、成长）、`0x1641cf0`（招式）和 `0x1641d78`（特性）。每张表从分配器创建，重置到静态变量（`0x1643e68`），再经 `0xf0ba9c` 追加到注册表 0x4763a18（u32 计数 0x4765a18，最多 0x400）。预留文件记录总数后按文件顺序插入，即可得到游戏机的节点列表。静态映像及五张表来自玩家自己的转储：main 与 SDK 来自 4.0.0 更新的 ExeFS（main 构建 ID `421c5411b487eb4d049dd065fec9547773e8e598`）；各 NSO 段按内存偏移放置，包含 .bss；RELATIVE 重定位按 main `0x8504000`、SDK 为 main + `0x4e6d000` 处理，再将 GLOB_DAT、JUMP_SLOT 和 ABS64 槽位绑定到首个导出符号的模块，main 优先于 SDK。表来自叠加基础游戏后的更新 RomFS（`arc/data.trpfs`，Oodle 经 `0xcc8750`）。M4 上读取需 3 秒，构建会话及 N 开始状态需 2.4 秒。

弱句柄条目大小 0x20 字节：u64 ID（u32 索引 | u32 代数 << 32），+8 为解析值，+0x10 为对象，u16 +0x18 为弱引用计数，u16 +0x1a 为强引用计数，u32 +0x1c 为状态（-1 已释放、-2 存活）。每块有 0x400 个条目（`0xc1adec`）；已释放 ID 进入由 `0xb44724` 扩展的 `deque<u32>`。

<a id="the-servers-flow-measured"></a>
### 服务器流程实测

以下规则来自为[提供对战服务](#serving-the-battle)中的脚本游戏机运行的参考程序服务器。按这些规则构建的服务器，在玩家获胜的九场完整对战中向游戏机发送相同的帧，通知也一致：

| 规则 | 实测结果 |
|---|---|
| 头部计数器 | 每次发送（广播或单次请求）使 `step` 增加 1；`round` 在消息 1 时为 0，从 0x11 起为 1，每次 0x15 和 0x25 都增加 |
| 每帧一个任务 | 消息 1 启动 Wild::Setup；全部槽位回应 1 后发送 0x11，全部槽位回应 0x11 后再过一帧结束 |
| 请求 | 没有任务运行的帧，对没有待回应消息的槽位提交请求（5）；每帧启动一个请求，顺序为槽位 0、2、3、4 |
| 命令 | 将槽位的 6 作为任务提交，向全部槽位发送回合（0x15） |
| 再次询问 | 槽位回应了发给它的全部回合后，下一帧再次询问 |
| 获胜 | 获胜回合的下一帧是空回合 0x25（20576 个零字节），再依次发送正文为 `00 00 01 00 01 00` 的 0x29、0x49、0x35、0x37；每条均等待全部槽位回应上一条。0x25、0x49 的最后回应后等 2 帧，其余在同帧发送 |
| 时间耗尽 | 正文为 `00 00 00 00 02 00` 的 0x2b（233 场中 63 场） |
| 通知 0x46 | 每个启动任务的帧，或无任务运行但读到回合回应（0x16）的帧，各有一条 |

<a id="serving-the-battle"></a>
### 提供对战服务

`bin/sv_host.py --raid-serve [NAME]` 在对战期间保持网络，并通过 `pokeldn.sv.raid_battle.RaidBattle` 从主持端站点提供服务：使用根据引导数据和两位 NPC 搭档创建的插件对战服务器（[对战服务器](plugins.md#a-battle-server)），以及游戏机主持端为自己保留的站点。pokeldn 不内置对战服务器；没有插件提供服务器时，此选项会被拒绝。此会话安排程序宝可梦、首领、站点索引 1 的一台游戏机（引导数据参与者 1、槽位 2）和两位 NPC 搭档，因此只允许一台游戏机加入。

| 部分 | 主持端发送内容 |
|---|---|
| 服务器发往游戏机的消息 | 目标地址为 (0x2713, 1, 2) 的帧 |
| 槽位 0、1、3、4 | 每个奇数步骤在 0.05 秒后以类型 + 1 回应；对槽位 0、3、4 的请求（5），回复类型 6 命令，令该槽位宝可梦用首个招式攻击首领，首领用首个招式攻击该宝可梦（[行动](#actions)） |
| 服务器读取的每条消息，包括游戏机自身的消息 | 转发给游戏机，目标地址 (0x2713, 3, 5) |
| 每个推动对战的服务器帧 | 在该帧消息后，由槽位 0 发送通知 0x46（步骤 0，4 字节全零正文），目标地址 (0x2713, 3, 5) |

每帧在 0x80 端口 0 上作为一条 deflate 压缩的可靠消息发送（标志 `COMPLETE_ZLIB`），实测最大压缩后为 903 字节。复现《朱》4.0.0 的服务器，其前六帧与零售版主持端发送的六条开始消息（`raid.HANDOFF`）顺序相同，除头部由栈填充的字节外一致，因此 `--raid-serve` 用它们替代 `HANDOFF`。

游戏机回应 0x37 后，或发送 0x37 五秒后，主持端停止服务并关闭网络。回应 0x37 本身会让服务器再次执行时间耗尽（[服务器流程](#the-servers-flow)），因此本地站点不回应它。失败（服务器抛出异常或构建失败）会停止服务，并像未指定该选项时一样交出网络；游戏机随后接管并自行运行对战（[运行对战服务端的站点](#which-station-runs-the-server)）。

<a id="joining"></a>
## 加入团体战

`bin/sv_join.py --raid-pokemon FILE` 加入场景 7 的网络，并作为加入方参与。游戏机玩家调查结晶，选择“大家一起挑战”后等待；应用的“太晶团体战（加入）”入口负责运行加入端。`pokeldn.sv.raid.RaidGuest` 和加入端按以下顺序执行：

| 步骤 | 加入方行为 |
|---|---|
| Net | 在消息标志 0x11 下回应 0x11 和 0x50 |
| Session | 不回应加入响应附带的站点列表，至少 1 秒后确认其重发，之后确认每个列表，并发送第 9 字节已设置的时钟请求 |
| 通道 | 将主机的六键表拆为四个键和团体战的两个键，公布四个键；0.24 秒后加入端口 2，表公布后 0.79 秒公布团体战键；将 0x7C 确认延迟 0.25 秒 |
| 身份 | 入座后 0.44 秒发送标准记录集（`pokeldn.sv.reference`），记录 1 使用训练家名称 |
| 大厅 | 再过 0.27 秒发送状态 0x18 和自身宝可梦；2 秒后发送状态 0x01 |
| 开始 | 收到主机的状态 0x0c 后发送状态 0x0d；准备就绪时就发送 0x0d 的加入方得到确认，但始终未显示为准备就绪 |
| 战斗 | 确认主机的 0x3480 0x93，每 0.5 秒发送 Session 类型 3 离开请求，直到收到类型 4（最多四次），然后离开网络；战斗中的实机《朱》未回应其中任何一次 |

在实机主机上，加入方以训练家名称出现在大厅，变为准备就绪，主机随后可以开始战斗；其宝可梦留在战斗中。

## 尚未解决

- 目标没有被击倒时，部分降低能力的追加效果前抽取 `chance(0)` 的含义。
- 玩家使用会注册处理函数并束缚目标的潮旋，命中妖精太晶首领时为何只造成 7 点伤害，而公式给出 14 至 17。

- GlueCode 调度器 `0x18beef4` 的监听器是否按字读取 `+0x4c`（监听器在运行时注册，第 1 至 3 组在 `0x18bf87c` 调用），以及谁消费 `0xe106a4` 填入的各席位队列（从 `0xe107ac` 调用 `0x113d5e0`）。+0x08 为零的消息 16 不进入任何队列，读取器按其分支后，`0xf5bc10` 在 `0xf5bc30` 返回。
- 消息 16 在加入方释放何项。服务器上的来源对象由 `0xfc363c` 推进，位于 G+0xa8，也等于 N+0x48 的 +0x128；`0x18915c4` 经 `0xfa493c` 将 `0x1849e10` 创建的对象填入该字段。它从自身 +0x48 的调度器中选取下一项已提交请求（[服务器流程](#the-servers-flow)）。

- RaidPoint 的字节 0x3b4 含义。
- 将服务器链接双端队列（`[link+0x48]`）发送到网络的代码。
- 消息 0x37 后，谁结束团体战。运行步骤 `0x2d383b8` 在 N+0x9e 的位 0、1 均设置，所有入座客户端步骤（N+0xb8..N+0xd8 处对象，`0xf59e54`，经 +0xd0 的成员指针）均返回 1（N+0x78..N+0x7c 字节），或 N+0xa0 设置时返回 1，表示对战结束。N 的构造函数清零 N+0xa0（`0x16b1058`），未发现设置它的代码。N+0x9e 的位 1 仅由外层序列 `0x1269824` 设置；团体战路径的位 0 则在选举对象 [N+0x138] 的 vf 0x68 返回真时设置（`0x2a1d428`：其 +0xca 仅由 vf 0x70 `0x2a1d920` 设置），同时将全部客户端标为完成（`0x2893238`）。没有服务器任务设置这些条件；客户端读取自身接收链接 [client+0x60]，它应由上述尚未定位的代码填入。
