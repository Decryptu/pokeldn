
<a id="online-trade"></a>
# 在线交换

在线交换连接远距离的两位玩家。每位玩家的开发板为自己的游戏机创建本地交换；两个应用通过公共 Nostr 中继匹配，并将各自游戏机提出的宝可梦传给对方。游戏机看到的仍是普通本地交换，但对方的宝可梦来自远端游戏机。项目没有自有服务器：中继为公共基础设施，且只处理加密事件。代码位于 `pokeldn/online/`；启动器参数为 `--online` 和 `--online-code`。

<a id="the-room"></a>
## 房间

两端运行同一游戏、使用相同密码时可以匹配。房间标识为：

    sha256("pokeldn online 1|<game>|<code or 'open'>")

结果是 64 位十六进制字符串。空密码为开放房间，任何使用同一游戏且不设密码的在线玩家都可匹配。《火红》和《叶绿》共用 `frlg`，《朱》和《紫》共用 `sv`，其他按功能目录中的游戏分组。游戏有连接密码时，使用游戏机自己的连接密码，玩家在游戏机和应用中各输入一次。八位数字提供 10^8 个房间；输入相同密码的玩家会互相匹配，与游戏自身的行为一致。

<a id="the-relays"></a>
## 中继

每个事件都是 Nostr 事件（NIP-01），类型为 21059，处于临时事件范围 20000-29999：中继只向当前订阅者转发，不保存内容。每个事件携带标签 `["t", <room>]`，发给指定应用时还携带 `["p", <its signing key>]`。每个应用使用一个订阅，请求从启动前十秒开始、包含房间标签的类型 21059 事件。

每次会话用新的 secp256k1 密钥签名（BIP-340 Schnorr，`pokeldn/online/schnorr.py`，已用 19 组 BIP-340 测试向量检查），因此两次会话之间不共享密钥。应用向所有连接的中继发布事件，并丢弃相同事件 ID 的重复副本。

| 中继 | 每 2 秒一条事件，共发送 8 条 |
|---|---|
| relay.primal.net、relay.snort.social、offchain.pub、relay.nostr.net、nostr.oxtr.dev、nostr-pub.wellorder.net | 8 条全部送达 |
| relay.damus.io | 4 条送达；对地址限速，随后暂时封禁 |
| nos.lol、nostr.mom | 因限速拒绝，没有送达 |
| nostr.wine | 拒绝，属于付费中继 |

第一行为默认中继集；`POKELDN_RELAYS`（逗号分隔的 URL）可替换它。offchain.pub 拒绝未知密钥的突发事件（“not in our web of trust”，即不在其信任网络中），接受按间隔发送的事件。在这些中继上，第二个应用到达后约 0.4 秒完成配对，344 字节记录约 0.15 秒送达。

《朱》和《紫》的两台实机各由一块开发板担任主机，已通过中继完成交换：双方游戏机显示对方提供的宝可梦，两边确认后都收到对方的宝可梦，屏幕均未出现错误。《火红》和《叶绿》实机也完成了同样的测试：双方队伍逐对交换，包括邮件和奖章，耗时约 4 秒；交换后再次传输队伍数据，回到了交换菜单。

同一张桌上的两台游戏机会直接找到彼此，例如使用相同密码搜索的《朱／紫》，或者玩家选择“成为领队”的《火红》。进行这种测试时，每台游戏机应使用不同的本地密码（或者选择“加入组”加入开发板的组），再用 `--online-code` 将两块开发板放入同一个在线房间。

<a id="stored-events"></a>
### 存储事件

在线交换不存储任何内容。在七个中继上测量了存储事件（relay.primal.net、relay.nostr.net、nostr.oxtr.dev、nos.lol、nostr.mom、offchain.pub、nostr-pub.wellorder.net）：类型 30402 的条目（NIP-99）和类型 1059 的封装（NIP-59），每个都使用新密钥。

| 行为 | 结果 |
|---|---|
| 来自新密钥的事件 | 35 个事件全部接受并可重新读取 |
| 设置了两小时后到期的 NIP-40 `expiration` 的 30402 | 1.1 小时后仍可读取；到期 6 分钟后所有中继均不再提供 |
| 使用相同 `d` 重新发布的 30402 | 一分钟内所有中继都只提供较新的事件 |
| 类型 5 通过 `e` 和 `a` 指定一条 30402 | 一分钟内所有中继都只提供类型 5 |
| 通过 `p` 密钥读取类型 1059 | 六个中继提供；relay.nostr.net 要求 AUTH，却拒绝全部类型 22242（“relay needs serviceUrl to be configured”，即中继需要配置 serviceUrl） |

中继会保留无到期时间的事件多久，尚未测量。

<a id="meeting"></a>
## 匹配

每个事件的内容使用房间密钥 `sha256("pokeldn room key|" + room)` 进行 AES-256-GCM 加密。内部消息如下：

| 消息 | 发送时机 | 内容 |
|---|---|---|
| `here` | 每 2.5 秒，发往房间 | 协议 1、X25519 公钥、训练家名字、应用版本、忙碌状态 |
| `invite` | 发往指定应用 | 训练家名字 |
| `yes` / `no` | 回复邀请 | 训练家名字 |
| `bye` | 发往非当前伙伴的应用 | 原因 |

应用只邀请签名密钥大于自己的空闲应用，优先选择已发现最久者；同时仅保留一个邀请，最长 6 秒。已发出邀请的应用对其他邀请回复 `no`。邀请被拒绝或未回复时，跳过该应用 10 秒。中继不保证顺序，因此伙伴的首条通道消息可能早于 `yes` 到达；它同样视为 `yes`（接受邀请）。

<a id="the-channel"></a>
## 通道

配对后的消息经过两层加密：外层 AES-GCM 使用房间密钥，包含发送方 X25519 公钥；内层 AES-GCM 使用：

    sha256("pokeldn pair|" + room + "|" + sorted("<signing key>:<x25519 key>" of both) + shared secret)

每条消息携带序号 `s` 及按顺序收到的最高序号 `a`。未确认消息每 2 秒重发；消息到达后 0.3 秒发送确认，以合并同时到达消息的确认。每 4 秒发送 ping 维持配对，伙伴静默 45 秒则视为离线。双方都尚未提出宝可梦时失去伙伴，应用会重新寻找其他玩家。

| 消息 | 含义 |
|---|---|
| `hello` | 训练家名字及应用版本，只发送一次 |
| `offer` | 第 *r* 次交换：本地游戏机提出的记录，base64 编码 |
| `withdraw` | 第 *r* 次交换：本地游戏机撤回提议 |
| `accept` / `unaccept` | 第 *r* 次交换：本地游戏机确认或撤回确认 |
| `refused` | 第 *r* 次交换：伙伴应用拒绝我们的记录及原因 |
| `done` | 本地游戏机完成第 *r* 次交换；下一次为 *r* + 1 |
| `ping`, `bye` | 保活及离开 |

<a id="what-crosses"></a>
## 传输内容

只传输游戏机提出交换的记录及交换状态，密钥、存档和文件都不传输。游戏机看到远端记录前，各应用会用 PKHeX 检查（`pokeldn.online.session.checker`）：

| PKHeX 检查结果 | 记录处理 |
|---|---|
| 无法解析、校验和错误、种类或形态不在游戏中、招式／道具／球种 ID 超出游戏表 | 拒绝，发送方应用显示原因 |
| 游戏尚未发布的携带道具或招式（“unreleased”；《剑》的道具到 1607） | 拒绝 |
| 其他合法性标记 | 允许提出交换，向接收玩家显示 PKHeX 标记 |

实机交换的记录也可能未通过 PKHeX 合法性分析，因此单独的合法性标记不会造成拒绝。

<a id="in-a-launcher"></a>
## 启动器中的流程

使用 `--online` 的主机启动器不会提供自行生成的宝可梦，而是提供交换伙伴游戏机的宝可梦。

1. 本地游戏机提出交换：通过 `offer` 将记录发送给伙伴。
2. 收到伙伴记录：启动器向本地游戏机提出该宝可梦。伙伴撤回提议时，也从本地游戏机撤回。
3. 本地游戏机确认：发送 `accept`。只有两台游戏机都确认后，启动器才发送自身确认，避免一端单独越过无法取消的阶段。
4. 交换完成：发送 `done`，从盒子开始下一次交换。

| 游戏 | 我们的提议 | 游戏机撤回自己的提议 | 我们撤回提议 | 双方游戏机确认后发送的确认 |
|---|---|---|---|---|
| 火红／叶绿 | 伙伴的队伍块（三块各 200 字节，邮件 220、奖章 40），本地游戏机对应块到达时逐块发送；`SET_MONS_TO_TRADE` 携带伙伴光标 | `READY_CANCEL_TRADE`（回复 `PLAYER_CANCEL_TRADE`）、`REQUEST_CANCEL` | `PLAYER_CANCEL_TRADE` | `START_TRADE` |
| Let's Go | 类型 2，包含伙伴 232 字节记录，回答游戏机步骤 | 撤回表决（状态 2）、离开（状态 4） | 无 | 已提出克隆上的 A 2，末尾字变为 2 |
| 剑／盾 | 20030，盒子命令 1；0x84 快照的队伍槽保留游戏机自身宝可梦 | 盒子命令 2（提议）、5（确认） | 盒子命令 2 | 盒子命令 4 |
| 晶灿钻石／明亮珍珠 | 0x13，回答游戏机消息 | 0x45 `{1}` | 0x45 `{1}` | 0x21 `{0, 2}`；安全阶段仍自动处理 |
| 传说 阿尔宙斯 | 选择器 4，使用游戏机计数器回答；已知伙伴记录后，以它回答展示消息（选择器 2） | 选择器 6 | 无 | 镜像游戏机的选择器 5 |
| 朱／紫 | 类型 2，包含伙伴的 348 字节正文 | 类型 4 `8000040100` | 类型 4 | 类型 3 |
| 传说 Z-A | 伙伴选择的预览，0.5 秒后发送选择记录 | `0103` | 下一轮的 `0103` | `0102`，随后 `0104` |

《火红／叶绿》在入座时交换整个队伍，因此各游戏机看到的是伙伴队伍，与两张卡带间交换相同。每个主机向自己的游戏机请求一对队伍块，直到伙伴游戏机发来对应块才发送自己的块；游戏机会无计时器地等待两块 [trade.c:1478]，因此两个主机不会互相等待。只有 PKHeX 能读取块中的每只宝可梦，才向游戏机发送该队伍块。选择记录以 `pick`（游戏机光标）发送，早于提出的宝可梦记录。

对方离开或连续 45 秒没有消息，视为撤回其提供的宝可梦：除非交换已经进入无法撤回的阶段，否则各主机会从自己的游戏机上撤下对方的宝可梦。《火红／叶绿》的领队只能回应加入方的动作，因此，对方离开后，游戏机当前和之后每次选择宝可梦都会得到 `PLAYER_CANCEL_TRADE`（显示“已取消”，返回菜单）；这与领队选择取消时的回应相同 [trade.c:1712]。之后在菜单选择取消即可离开。如果对方在队伍传输到一半时离开，则以空队伍完成传输。玩家在菜单选择取消时，会立即通知对方。实测《火红》和《叶绿》：一方选择宝可梦，另一方取消并离开；前者显示取消消息并返回菜单，再选择取消即可离开房间。

《剑》的连续交换已经可以提供与快照槽不同的记录（[《剑》的交换](swsh_trade.md)），实际交换的是内容 50 的记录。

<a id="the-gts"></a>
## GTS

GTS 让从未同时在线的玩家交换银行中的宝可梦。玩家从[银行](gui.md#the-bank)选择宝可梦挂牌，并指定想要的种类和等级范围；另一位玩家用自己的宝可梦回应，挂牌方下次打开应用时完成交换。游戏机不参与：收到的宝可梦放入银行，再由银行传送到游戏。代码：`pokeldn/online/gts.py`（事件）、`pokeldn/app/gts.py`（银行侧）和应用的 GTS 页面。

| 事件 | 类型 | 签名方 | 内容 |
|---|---|---|---|
| 挂牌 | 30402 (NIP-99)，`d` 为随机 ID | 为该挂牌单独生成的密钥 | JSON：协议 1、游戏、PKHeX 读取的宝可梦信息（种类、等级、性格、特性、球、道具、招式、初训家）、记录 SHA-256、想要的种类和等级、训练家名称、状态、成功的交换请求 |
| 交换请求 | 1059，`p` 为挂牌密钥 | 为该请求单独生成的密钥 | 加密：挂牌的 `d`、游戏、记录、训练家名称 |
| 回应 | 1059，`p` 为请求密钥 | 挂牌密钥 | 加密：请求 ID，以及挂牌记录或拒绝原因 |
| 删除 | 5 (NIP-09) | 被删除事件的密钥 | 无 |

挂牌携带 `["t", "pokeldn-gts"]`、`["t", "pokeldn-gts-has-<species>"]` 和 `["t", "pokeldn-gts-wants-<species>"]`，中继服务器因此能按任一种类过滤；同时携带 NIP-99 的 `title`、`summary`、`status`、`published_at`，以及 30 天后的 NIP-40 `expiration`。加密正文使用 AES-256-GCM，密钥为 `sha256("pokeldn gts|" + x)`，其中 x 是一端私钥与另一端仅含 x 坐标的公钥做 ECDH 后的 x 坐标（`schnorr.shared_x`）。应用信任存储事件前会检查其 ID 和签名。

| 步骤 | 行为 |
|---|---|
| 存入 | PKHeX 必须判定宝可梦合法；记录及 `.json` 从银行移至 GTS 文件夹，挂牌发送到每个中继服务器 |
| 提出交换 | 宝可梦必须合法，且符合种类和等级要求；暂时移出银行，加密请求发往挂牌密钥 |
| 挂牌方打开应用 | 请求发给挂牌密钥的加密消息；按时间由早到晚回应已存储请求，第一个合法且符合需求的请求完成交换，其余全部拒绝 |
| 交换 | 回应携带挂牌记录；重新发布状态为 traded、包含成功请求 ID 的挂牌，收到的记录存入银行 |
| 请求方打开应用 | 核对回应记录与挂牌的 SHA-256 后存入银行；被拒绝、挂牌与其他请求交换或被撤下时，将自己的宝可梦返还银行，并删除请求 |
| 挂牌到期 | 30 天后宝可梦返还挂牌方银行，不再处理交换；请求方在到期一小时后、服务器送完所有存储回应且没有对应回应时取回宝可梦 |
| 撤下 | 重新发布状态为 withdrawn 的挂牌并返还宝可梦；之后的请求被拒绝 |

每条挂牌和请求对应 `Documents/pokeldn/GTS` 下的一个文件夹（设置 `POKELDN_DATA` 时为其下的 `GTS`），保存 `state.json`（私钥、签名事件、已发送回应）及记录。回应先写入再发布，连接到每个服务器后重新发送所有有效事件，因此途中丢失的回应可在下次打开应用时交付。已完成文件夹在最后修改 60 天后删除。

两个各自有银行的应用通过七个服务器交换，始终只有一端打开：七个服务器均存储挂牌、请求和回应（OK true）；挂牌方打开时完成交换，请求方打开时将挂牌记录存入银行；删除后，七个服务器对测试密钥只返回类型 5 事件。全过程约 30 秒。

使用[已存储事件](#stored-events)中的七个服务器；`POKELDN_GTS_RELAYS`（逗号分隔）可替换它们。relay.snort.social 不存储内容，因此未加入。

正常应用遵守这些规则，修改版应用未必遵守。挂牌方应用可以留下收到的宝可梦而不回传，挂牌也可以展示其实际没有的宝可梦；SHA-256 只能事后判断，不能提前保证。没有可信第三方就无法实现公平交换（Pagnia 与 Gaertner，1999）。

<a id="unresolved"></a>
## 尚未解决

- 中继服务器在 24 小时以后保存挂牌或加密消息多久。24.1 小时时，七个服务器都返回了到期时间为 3 天的 30402、无到期时间的 30402 和类型 5；六个返回类型 1059 加密消息。
- 各游戏机在已持有主机提议时，如何回应主机撤回：包括《剑》的盒子命令 2（玩家停在确认画面时，加入端发送命令 1 再发 2，四秒后主持端游戏机开始离开）、《朱》的类型 4、Z-A 的 `0103`、《晶灿钻石》在游戏机选择后的 0x45。《Let's Go》和《传说 阿尔宙斯》则继续等待。
- Z-A 是否接受在自己的选择前未发送预览的选择记录，以及《传说 阿尔宙斯》是否接受覆盖已持有记录的第二条选择器 4。
- 实机在盒子中等待伙伴提议及确认超过一分钟后，还能等待多久。
